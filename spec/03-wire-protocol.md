# Wire Protocol

Event-based WebSocket protocol between server, hosts, and surfaces. Built on the [`happy-wire`](https://github.com/slopus/happy/tree/main/packages/happy-wire) package structure with patch-specific events.

## Goals

- One message = one discrete event. Surfaces render a stream of events.
- Every event has a monotonic `seq` per chat so dropped connections can replay (`12-error-and-offline.md`).
- No request/response. Both sides push events; correlation via `id` fields where needed.

## Idempotency

`chat.input` carries a client-generated `localId` (UUID). Host enforces uniqueness per `(chatId, localId)` — a duplicate post (retry on flaky network, surface reconnects mid-send) is dropped without creating a duplicate user message. Agent-emitted events (`chat.message`, `chat.tool_call` etc.) are emitted exactly once by the host and carry no `localId`.

carrying `daemonId`, and arrives with its `17-cli.md` § Commands entry and its

### Answering with content (`approve_with_edits`)

Most permissions are a yes or a no, and `approve` / `deny` carry everything the
host needs. Some are not: the user's answer IS content, and it has to travel
back into the tool call before it runs. `approve_with_edits` is that channel —
one string, `editedNewString`, which the host substitutes into the pending
tool's arguments per tool before granting permission. Where it lands depends on
the tool: `Edit.new_string`, `Write.content`, `NotebookEdit.new_source` (the
Monaco-edited file content — `14-design-web.md` § Diff editor), and
`AskUserQuestion.answers` (the user's chosen options, JSON-encoded — see below).
A decision of `approve_with_edits` naming a tool with no such argument is an
error, not a plain approval: the host denies the call and says so with a
`chat.error` (`invalid_frame`), because approving a tool whose answer was
dropped is exactly the silent-empty-answer failure this channel exists to fix.

Required means present and a string, not non-empty. The empty string is a
meaningful answer for the file-edit tools — it is how an edit that deletes the
content is approved — so a surface sends it through unchanged rather than
refusing it or downgrading to a plain `approve`. A missing or null
`editedNewString` is still an error, since that is an answer that was lost
rather than an answer of nothing.

**`AskUserQuestion` rides this channel deliberately, rather than getting a field
of its own.** Its answers are `{[questionText]: selectedOptionLabel}` — a
multi-select joins its labels with `, ` into that one string — JSON-encoded into
`editedNewString`. A dedicated field would be the more obvious design and is the
wrong one here: every event schema is `.strict()` and `decode` throws
`WireDecodeError` on an unknown key, dropping the whole frame. Hosts OTA
on their own schedule and routinely lag the web surface, so a new field would
make a new surface talking to an older host drop the permission response
outright and leave the chat waiting forever. Reusing a field that already
round-trips end to end degrades instead of breaking: an older host decodes the
frame, finds no substitution rule for `AskUserQuestion`, and approves the call
with no answers — the old (wrong, but not stuck) behaviour.

(§ Forward compatibility has since lifted that constraint: a host ignores a
field it does not know rather than dropping the frame. This channel stays as it
is because it works end to end and the surfaces are built on it — but it is why
the design reads the way it does, and a NEW field elsewhere no longer needs this
contortion.)

### Files (surface ↔ host)

Backing the editor rail's file browser (`14-design-web.md` § File browser). Paths resolve on the chat's own host, inside the chat's folder.

| Type                     | Direction      | Payload                                                                                                                                                                                                    |
| ------------------------ | -------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `patch.files.request`    | surface → host | `{requestId, chatId, path, content?}` — list `path`'s entries, or read that one file when `content`                                                                                                        |
| `patch.files.response`   | host → surface | `{requestId, entries?, content?, error?}` — `entries[]` is `{name, kind}`; a missing file or a path escaping the chat folder errors                                                                        |
| `file.write`             | surface → host | The editor save, listed under Surface events above                                                                                                                                                         |
| `patch.file_op.request`  | surface → host | `{requestId, chatId, op, path, to?}` — `op` is `create` (empty file), `create_dir` (one directory), `delete` (one file or one EMPTY directory) or `rename` (to `to`, inside the same folder)               |
| `patch.file_op.response` | host → surface | `{requestId, ok, path?, error?}` — `path` is where it landed (`to` for a rename); `error.code` is one of `chat_not_found`, `path_escape`, `not_found`, `exists`, `not_empty`, `missing_target`, `internal` |

Unlike the listing above, these four change the disk, so the pair is a REQUEST/RESPONSE with an acknowledgement rather than a fire-and-forget surface event: the user is told the outcome, and "the frame went somewhere" is not an outcome. A host too old to know the type drops it, the server's wait times out and the surface reports a failure — an operation can never read as having succeeded because nobody answered.

Nothing here overwrites and nothing recurses. `create` and `rename` refuse an occupied destination (`exists`), `delete` refuses a directory with contents (`not_empty`), a destination's parent directory is never created implicitly (`not_found`), and neither the chat folder itself nor anything a symlink resolves to outside it is a legal target (`path_escape`). Refusals carry the host's own sentence, with host paths stripped — the surface is told the chat-relative path it asked about and nothing about the machine's layout.

### Host files (server ↔ host)

Backing the phone's host Files screen (`15-design-mobile.md` § Host files and terminal; behaviour in `02-daemon.md` § Host files). Addressed to a host by `daemonId` and an absolute path — no chat. Surfaces reach it over REST, which round-trips one request to the named host:

- `GET /api/hosts/:daemonId/files?path=` → `{path, parent, entries[]}` (no `path` = home)
- `GET /api/hosts/:daemonId/files/content?path=` → `{path, content, size, version}`
- `PUT /api/hosts/:daemonId/files/content` `{path, content, baseVersion}` → `{path, size, version}`

The gate is the folder browser's: a live surface credential and a registered host (`unknown_host`, 404). An offline host is refused up front (`host_offline`, 503) and a host that does not answer in 10 s is a 504. The response is never relayed to other surfaces.

| Type                        | Direction     | Payload                                                                                                                                                                                                                                                                                                                                                                              |
| --------------------------- | ------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `patch.host_files.request`  | server → host | `{requestId, daemonId, op: 'list'\|'read'\|'write', path?, content?, baseVersion?}`                                                                                                                                                                                                                                                                                                  |
| `patch.host_files.response` | host → server | `{requestId, daemonId, ok, path?, parent?, entries?, content?, size?, version?, error?}` — `entries[]` is `{name, type: 'file'\|'dir'\|'other', size?}`; `error.code` (HTTP status) is one of `path_invalid` (400), `not_found` (404), `not_a_directory` (400), `not_a_file` (400), `too_large` (413), `binary` (415), `conflict` (409), `permission_denied` (403), `internal` (502) |

### Chat search (server ↔ host)

Backing `GET /api/chats/search?q=&limit=&offset=` (`04-chats-and-folders.md` § Search). The gate is the other chat routes': a live surface credential. `q` is trimmed and must be at least 2 characters; `fullText` is `true` (default) or `false` (names only; also `1`/`0`), anything else is a 400; `limit` is 1–50 (default 20), `offset` 0–199; anything else is a 400. The server sends one request to every online registered host, asking for its top `min(offset + limit, 200)` hits; the merged page is therefore exact. A host has 15 s to answer — long enough for a first search that waits on a freshly started host's index build. The server stamps each hit's `jobId` from its own chat registry, sorts under the shared ordering (`lastUpdated` descending, then `chatId`), and answers 200 with `{query, hits[], total, nextOffset, hosts[]}` — `nextOffset` is `null` on the last page, and `hosts[]` names every registered host as `searched` (with `searchedChats` and `transcriptsMissing`), `offline` (not asked; the server instead searches its own mirror of that host's chats and reports `mirroredChats` — see `04-chats-and-folders.md` § History — server mirror), `timeout` or `error` (with `message`). The response carries message text, so it is never relayed to surfaces over the socket.

A hit is `{chatId, daemonId, name, preview, folder, status, section, pinned, snoozedUntil, lastUpdated, jobId, nameMatch, nameHighlights, messageMatches, snippet}`. `section` is one of `manager`, `channels`, `pinned`, `folders`, `snoozed`, `archived`. `snippet` is `null` for a name-only hit, else `{text, highlights, role: 'user'|'assistant', seq, createdAt}`, where `text` is a whitespace-collapsed window of the message with `…` marking a cut end, `seq` and `createdAt` may be `null`, and every `highlights` / `nameHighlights` entry is a `[start, end)` character range into its string.

| Type                         | Direction     | Payload                                                                                                              |
| ---------------------------- | ------------- | -------------------------------------------------------------------------------------------------------------------- |
| `patch.chat_search.request`  | server → host | `{requestId, daemonId, query, limit, fullText?}` — `fullText: false` searches names only                             |
| `patch.chat_search.response` | host → server | `{requestId, daemonId, ok, hits?, total?, searchedChats?, transcriptsMissing?, error?}` — `error.code` is `internal` |

### Cross-chat tools

A cross-chat call whose target is on the calling chat's own host is short-circuited in-process. One naming another host goes over these frames, relayed by the server to that host. Surfaces see them either way, so cross-chat activity renders as an audit trail.

`patch_spawn` names its host directly (`daemonId` on the frame), since the caller is choosing a machine to create a chat on. `patch_peek`, `patch_history` and `patch_send_to` take only a `targetChatId` — the caller learns which chats exist from `patch_list_chats`, not which host each is on — so the server resolves the owning host from its chat mirror and relays there.

A call naming an offline host, or a `targetChatId` no host has ever reported, returns an error to the calling agent, naming the problem, within the turn. A tool result is part of a turn in progress, so it resolves rather than buffering the way `chat.input` does, and the agent decides what to do about the host being down.

The same holds for a host that is ONLINE and REFUSES: a cross-host call is answered by the named/owning host with its own `.response`, and the calling agent's tool call resolves on that answer — the real result, or that host's own error. A refusal reaching only the target's log would leave the agent believing a call that never landed had succeeded.

A request frame carries `requestId` only when it is a genuine cross-host relay the caller is waiting on; the same frame with no `requestId` is a same-host call already resolved in-process, kept on the wire purely as an audit record, and the server never relays it.

| Type                     | Payload                                                                                                                                                                             |
| ------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `patch.peek.request`     | `{sourceChatId, targetChatId, requestId?, limit?}`                                                                                                                                  |
| `patch.peek.response`    | `{requestId?, sourceChatId, targetChatId, ok, result?, error?}` — `result` (iff `ok`) is `{ chat_state, events, truncated }`                                                        |
| `patch.history.request`  | `{sourceChatId, targetChatId, fromSeq?, limit?, requestId?}`                                                                                                                        |
| `patch.history.response` | `{requestId?, sourceChatId, targetChatId, ok, result?, error?}` — `result` (iff `ok`) is `{ events, nextFromSeq? }`                                                                 |
| `patch.send_to`          | `{sourceChatId, targetChatId, message, requestId?, voicePrefix?}`                                                                                                                   |
| `patch.send_to.response` | `{requestId, sourceChatId, targetChatId, ok, error?}`                                                                                                                               |
| `patch.spawn`            | `{sourceChatId, daemonId, folder, model?, prompt, requestId?}` — `daemonId` names the host; `model` omitted takes the host's last-used; `requestId` present when a host must answer |
| `patch.spawn.response`   | `{requestId, sourceChatId, daemonId, folder, ok, chatId?, error?}` — the named host's outcome. `chatId` iff `ok`; `error` iff not                                                   |

### Browser tunnel (host ↔ host, relayed by server)

Backs `02-daemon.md` § Route through. A host whose Browser settings name
another host as its route opens a stream for each connection its local SOCKS5
listener accepts; the server relays every frame of it to the named routing
host, and relays that host's answers back the same way, for as long as the
stream stays open. Unlike the cross-chat tools above this is never a
request/response pair waiting on one answer — `streamId` alone correlates
every frame of one stream in both directions, and `ready`/`data`/`error` can
arrive from either side.

`open` names the routing host directly (`daemonId` on the frame) and is
refused immediately, naming the problem, if that host is unregistered or
offline — browsing never falls back to a direct connection. A routing host
that goes offline mid-stream gets the same treatment: the other side is sent
`error` and the stream is dropped, rather than left open against a machine
that can no longer answer it. `close` from either side ends the stream and the
server forgets it.

| Type                         | Payload                                                                                                                             |
| ---------------------------- | ----------------------------------------------------------------------------------------------------------------------------------- |
| `patch.browser_tunnel.open`  | `{streamId, daemonId, host, port}` — `daemonId` names the routing host asked to make the real outbound connection                   |
| `patch.browser_tunnel.ready` | `{streamId}` — the routing host made the real connection; the browsing host may now send `data`                                     |
| `patch.browser_tunnel.data`  | `{streamId, data}` — raw bytes, base64, in either direction                                                                         |
| `patch.browser_tunnel.close` | `{streamId}` — either side ending the stream cleanly                                                                                |

### Audio relay over the host link (server ↔ host)

Backs `07-voice-app.md` § Voice is a per-host capability's tunnelled path —
the DEFAULT way `/audio/:sessionId` reaches a voice session on a host that
has not declared a direct `audioRelayHost` (which is every host except one
co-located with the server, unless an operator has set one explicitly). A
host is never itself internet-reachable (`01-server.md` § WebSocket hub —
it only dials out), so instead of the server dialling in, every frame of the
session is carried over the SAME outbound link the host already holds,
multiplexed by `sessionId`. The host bridges those frames to its own LOCAL
audio WSS (`ws://127.0.0.1:<audioPort>/audio/:sessionId`) exactly as a
co-located surface would reach it directly — `audio/server.ts` runs
completely unmodified on that end, so it cannot tell a tunnelled connection
from a direct one.

Shaped like Browser tunnel above (open/frame/close over a persistent,
server-relayed correlator) with one addition: `frame.binary` marks whether
the inner WS frame it carries was text or binary, because a voice session's
inner stream mixes BOTH (JSON control frames and raw PCM16) on one socket,
unlike the browser tunnel's byte-opaque TCP stream. `open` travels server →
host only; `ready` is informational (the server does not wait for it —
frames sent before the host's local bridge is open are queued there, same
discipline as the direct-dial path's own queue-until-open); `frame` and
`close` travel in either direction; `error` travels host → server only, and
the server turns it into the surface-facing `audio.error {code:
'host_unreachable'}` — NO FALLBACK to any other pipeline.

| Type                      | Payload                                                                                         |
| ------------------------- | ----------------------------------------------------------------------------------------------- |
| `patch.audio_relay.open`  | `{sessionId}` — server asks the host to bridge this session to its own local audio WSS          |
| `patch.audio_relay.ready` | `{sessionId}` — the host's local bridge socket is open (informational)                          |
| `patch.audio_relay.frame` | `{sessionId, data, binary}` — one inner WS frame's bytes, base64, in either direction           |
| `patch.audio_relay.close` | `{sessionId}` — either side ending the bridge cleanly                                           |
| `patch.audio_relay.error` | `{sessionId, code, message}` — `code` is `connect_failed` (the host's own local connect failed) |

### Job-trigger events

No dedicated event type. When a job trigger (cron / webhook / Todoist) fires server-side, the server emits the action event directly — a `chat.spawn_request` or a `chat.input` (`08-triggers-and-jobs.md` § Action) — targeted at the host the action carries, identical to what a surface would emit. The host does not know or care whether the event came from a user or a fired trigger.

Job CRUD itself goes over HTTP to the server (see `01-server.md` endpoints), not over the WebSocket. The Manager / Speakers threads invoke `patch_job_*` tools that the host implements as HTTP calls to the server, authenticated with the host's `daemonKey`.

### Hooks (server ↔ host)

Backing `POST /api/hooks/check` (`20-hooks.md` § Checking a user*message). A
surface's check request is plain REST, never the socket — it is a
request/response, not a stream a reconnect needs to replay. The server
resolves which hooks match, then sends one `hook.check_request` per matching
hook to the chat's own host, all fired together, each with its own
`requestId` and the hook's own `timeoutMs`; a host that doesn't answer in time
is that run's own timeout (`20-hooks.md` § Outcome), not a dropped frame.
Hook CRUD is REST only, exactly like jobs (`08-triggers-and-jobs.md` §
Job-trigger events): `patch_hook*_`cross-chat tools are HTTP calls the
host makes to the server with its`daemonKey`, same as `patch*job*_`.

An `agent_response` check (`20-hooks.md` § Checking an agent_response) has no
surface asking it, so the HOST starts it: one
`hook.agent_response_check_request` per settled turn, carrying the agent's
full reply and a deterministic tool-call tally it already has without a
round trip. The server resolves matching `agent_response` hooks and
dispatches each with the SAME `hook.check_request` / `hook.check_result` pair
the `user_message` path uses — `reply` standing in for `message`,
`toolCallsSummary` riding in `context` — then reports every result back in
one `hook.agent_response_outcome`, unaggregated: the host decides what a
block/advise/failure means for the chat, not the server. `checkId` is
minted by the host and echoed back so a stale answer (a slow round-trip
a newer turn has already superseded) is recognisable and ignored.

| Type                                | Direction     | Payload                                                                                                                                                                                      |
| ----------------------------------- | ------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `hook.check_request`                | server → host | `{requestId, daemonId, hookId, kind, script?: {command}, prompt?: {instructions, model}, timeoutMs, context: {message, chatId, folder, daemonId, specialThread, toolCallsSummary?}}`         |
| `hook.check_result`                 | host → server | `{requestId, hookId, status: 'ok'\|'failed'\|'timeout', decision?: 'pass'\|'advise'\|'block', analysis?, suggestion?, error?, durationMs}` — `decision` present only when `status` is `'ok'` |
| `hook.agent_response_check_request` | host → server | `{daemonId, chatId, checkId, folder, specialThread, reply, toolCallsSummary}`                                                                                                                |
| `hook.agent_response_outcome`       | server → host | `{daemonId, chatId, checkId, results: HookRunResult[]}`                                                                                                                                      |

## Forward compatibility

Patch ships as five independently-deployable layers down two unrelated delivery
paths (`11-deployment.md`), so at any moment some reader is older than its
sender: a phone that was off during the deploy, a desktop shell that has not
restarted, a host that OTAs on its own schedule. The rule for what a
reader does about that is:

**Strict at ingress. Tolerant, and narrowly so, at every reader that can be
older than its sender.**

| Reader                          | Decoder        | Why                                                                                                                                                                                                                                       |
| ------------------------------- | -------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Server ← surface, server ← host | `decode`       | The server is the protocol's referee, and is never older than anything talking to it: every client artifact is published by the deploy that ships the server. An unknown key arriving here is a typo, not the future, and has to be loud. |
| Web surface, mobile surface     | `decodeCompat` | Routinely older than the host whose frames they render.                                                                                                                                                                                   |
| Host ← server                   | `decodeCompat` | Hosts OTA on their own schedule and routinely lag the server.                                                                                                                                                                             |

`decodeCompat` tolerates exactly two things, both of which mean "my sender is
newer than me", and nothing else:

1. **An unknown field on a known event.** The key is stripped and the frame is
   re-validated in full. If it does not then pass on its own terms, it is
   refused exactly as before.
2. **An unknown event type.** The frame is dropped quietly and counted. There is
   nothing a build can do with an event it has never heard of, and a banner per
   frame is worse than nothing.

Everything else — a missing required field, a wrong type, a bad enum, invalid
JSON — still throws `WireDecodeError` and still reaches the user as an error.
So does a frame that carries an unknown key **and** a real error: forward
compatibility is not cover for a bug.

This is not a fallback, which the principles forbid (`principles.md`). A
fallback invents a value the sender did not send. This discards a value the
reader cannot use, and says so: both kinds are counted per process
(`wireCompatStats()`) and reported by the connection diagnostics screen
(`12-error-and-offline.md` § Connection diagnostics screen). A tolerated FIELD
is drift, reported and passing. A dropped event TYPE is a build missing
behaviour its agent already has, so it FAILS the check and tells the user to
update that surface — which is the "update me" an explicit protocol-version
handshake would have bought, without a second thing to keep in step.

**Why not strict everywhere plus a version handshake.** A handshake tells a
stale surface it is stale; it does not let it keep working, and refusing the
whole session over one added field is a worse outage than the field. It also
needs a number bumped by hand on every change — a thing to forget — where this
needs nothing.

**What this buys.** Before it, one added field on a high-frequency frame took
out every surface that had not taken the matching OTA. `chat.state` drives the
sidebar and the chat view, so such a surface did not degrade, it stopped and
showed a wall of error banners. It was masked only because `pnpm run deploy`
ships every surface at once — not for a phone that was off, and not for a shell
that had not restarted. It also meant a new field could not be added without a
lockstep deploy, which is visible in this protocol's own design scars: see
§ Answering with content, where `AskUserQuestion` rides an existing field
because a new one would have broken older hosts.

**What it does NOT license.** A field may be added; a field may not change
meaning, and a required field may not be removed or narrowed. Tolerance is for
additions only — an older reader ignoring an addition still renders something
true, where a reader given a re-used field renders something false. A breaking
change is still a breaking change, and needs a new event type.

**Adding a VALUE to an existing enum is still breaking**, and deliberately so.
An unknown key can be ignored and leave the frame true; an unknown enum value
cannot — a new `chat.state.activity` an older surface has never heard of has no
honest rendering, and picking a near neighbour would be the fallback the
principles forbid. So `decodeCompat` refuses it, loudly, like any other invalid
value. Carry the new state as a new optional field instead, or design the field
open from the start and make every reader handle "something I don't know" as a
rendered state of its own.

**One wrinkle, deliberately not fixed.** Strictness is per object and is not
uniform today: named nested schemas (`RateLimitWindow`, `TodoItem`, `PendingWake`)
are `.strict()`, while some inline nested objects are not and already strip
unknown keys. `decodeCompat` makes the difference immaterial to readers, so it
is not worth a sweep through 169 schemas to make it consistent.

## Meeting events

Surface → host (relayed by the server; each adds the chat to the surface's watched set): `meeting.control_request {chatId, action: start|pause|resume|end}`, `meeting.get_request {chatId}`, `meeting.audio {chatId, source: mic|system, audioBase64}` (16 kHz mono PCM16 WAV), `meeting.action_request {chatId, actionId, decision: do|dismiss}`.
Host → surfaces: `meeting.state {chatId, meeting: MeetingState | null}`, the whole state each time; detail-level, so only surfaces watching the chat receive it. A refused request comes back as `chat.error`. See `14-design-web.md` § Meeting mode.

## Encoding

JSON over WebSocket text frames, except the audio session's PCM frames, which are binary (§ Audio session).

EdDSA-JWT in `hello` frame. Server verifies via stored Ed25519 public key and keeps the socket alive. See `10-auth.md`.
