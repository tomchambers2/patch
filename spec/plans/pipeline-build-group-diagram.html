pipeline-build-group  how one group runs

One run builds a group and verifies it against its plan-encoded e2e tests on a single shared live stack. Passing tests are skipped; only pending/failed ones execute; fix-loops touch only failures; every result is written back to the plan, which is the durable ledger. The orchestrator is pure mechanism — it never authors or narrows what gets tested.

1 Load tests

Read-only agent reads the plan, returns the group's encoded tests verbatim. The workflow filters out everything already pass — only pending/fail survive. no scope written by the orchestrator

2 Build  →  Confirm

Builder self-certifies (vitest / mocks allowed — we don't trust builders to run the app). A dumb gate sees only the table + a code all-pass check. This is not the real gate — the encoded tests are.

3 Provision shared stack

Bring up one live app stack (e.g. docker compose -f docker-compose.test.yml up -d), wait for healthz, hand its URL to every executor. one stack, not one-per-agent

4 Test  →  Confirm

Execute (not enumerate) only the pending tests against the live stack, routed by surface. On fail: fix agent repairs the failing ids, then only those re-run. A dumb gate fed only the rendered results decides pass/fail.

backend → curl frontend → playwright cli → patch CLI

5 Discover  · once, open-ended

One general-reviewer uses the app like a naive user to catch what the checklist missed. Output is proposed tests back to the plan — it does not gate.

6 Persist  →  Teardown

Mechanical writer sets each test's status by id in the plan, marks the group complete iff all pass, then tears the stack down. Plan writes are keyed to the gate — never to orchestrator judgement.

Why it can't weasel

Tests are frozen upstreamAuthored at plan-time by a party with no stake in passing. The orchestrator only reads them — it can't narrow scope or soften a verdict.
The gate is dumb on purposeConfirmation sees only id · STATUS · evidence. A hedge in the evidence ("mocked", "couldn't exercise") is visible; "deferred" can't be expressed — status is a hard pass|fail enum.
Real app, not unit testsExecutors drive the live shared stack (curl / playwright / CLI). A behaviour you can't exercise is a fail, never a pass.
The plan is the ledgerPer-test status persists, so re-runs & interrupts skip what's green — efficiency and crash-resilience from the same move.
