# Special Threads — Manager, Speakers

Two persistent single chats, each owning its own conversation history. They differ from regular chats in two ways: they have dedicated ingress surfaces, and they correspond 1:1 to a singular always-there ingress channel that doesn't go away.

## Why these two

Each thread embodies a singular channel that exists in the user's world independently of patch:

- Manager — the meta-operator. The single chat with an opinion about all the other chats. There is exactly one of these because there is exactly one user asking system-wide questions ("what's running?", "dispatch agent two"). It earns a permanent place because there is no other entity in patch with a cross-chat view.
- Speakers — corresponds to the physical voice devices in the user's home (kitchen, bedroom, living-room — HA Voice PE units re-flashed with patch firmware). Audio from any of them streams here. The thread is the persistent ledger of every spoken interaction across every device.

The pattern is singular ingress channel ↔ singular thread. Two is the right number because that's how many singular always-there channels there are: meta-orchestrator, in-home-voice. Adding Slack or Teams does not get a third special — those are normal chats fed by webhooks (see day-in-the-life §2).

These threads are not debug surfaces. They are how patch reaches the user (Manager rings; Speakers speak via TTS), and how the user reaches patch from environments where opening a project chat is wrong (a voice device, an orchestration question that spans projects).

## What they share

Both are agent sessions running on the host (same as any other chat). They differ from regular chats in two ways:

1. Dedicated ingress surfaces. Regular chats are reached via the generic surfaces (CLI / web / phone). These two have ingress-specific plumbing (voice-device audio WSS, Manager voice queue).
2. A defined role, expressed in a `CLAUDE.md` the user owns. Patch doesn't inject system prompts at runtime (per `principles.md`).

The toolset is not what makes them special — every chat in patch has the same tools available. Ingress and role are.

Each thread is a single chat. Each grows forever (session resume preserves history across queries).

## Where special threads run

The two special threads are singletons, and live on the account's home host.
The home host is set when the first host registers and is changeable from every
surface — Settings → Hosts on web and mobile, `patch hosts set-home` on the
command line (`17-cli.md` § Commands). Only the home host creates the thread folders and announces the threads: a host that
is not home has none, and the server passes on nothing a non-home host says about
them. Changing the home host creates the threads on the new host, leaving the old
transcripts readable on the previous one.

Through the cross-chat tools the Manager reaches any host: `patch_spawn` takes a
host alongside the folder.

Each special thread has a folder in the home host's state directory, under
the home directory of the user that host runs as:

```
~/.patch/threads/manager/
~/.patch/threads/speakers/
```

These are absolute paths on the home host, resolved from that user's `HOME` and
nothing else. They sit beside the host's other host-local state (`~/.patch/chats/`,
`~/.patch/daemon.sock` — `02-daemon.md` § Stack), so the host needs no notion of
a startup directory, a base directory or a configured root to find them, and an
OS-managed service that starts at boot lands on the same two paths every time.

These two folders are patch's own bookkeeping, not the user's projects, so no
surface offers one as a folder to work in. They are excluded from every recent
list, every folder picker, and every folder DEFAULT — by chatId where a chat is
in hand, and by path otherwise, since a folder arriving through the server's
roster or a host's registry carries no chat (`04-chats-and-folders.md` § Folders
→ Recent-folder selection rule). This matters most for the defaults: a special
thread is very often the most recently updated chat on the account, because it is
where automation lands, so an unfiltered most-recently-used seed points new work
at `threads/manager`.

On first host start, patch creates these folders and an empty `CLAUDE.md` in each. The file's content is the user's; patch creates it empty and leaves it alone. The user fills it in if they want role-specific guidance ("be concise, you're being heard aloud" for Speakers, "ring me only on urgent voice events" for Manager, etc.).

What a thread inherits is the host user's own agent configuration — `~/.claude/CLAUDE.md`,
`~/.claude/skills/` and the rest of that user's settings — the same configuration
every other chat on that host reads (`02-daemon.md` § Runtime and installation), because
the host runs as that user. The `patch-cli` skill is installed into that directory by
the host (`17-cli.md` § Skill), so a special thread knows patch's own surface area.
The per-thread `CLAUDE.md` layers thread-specific guidance on top of that without
touching general project conversations.

To give a thread more than that, write it into the thread's own `CLAUDE.md`, which is
the file patch creates for exactly this and never edits.

What sits in these folders is the thread's own working state: its `CLAUDE.md`, and whatever the agent writes while it runs. The broadcast records the Speakers thread reads when the user replies are server state instead (`09-notifications.md` § The broadcast log), because the machine that delivers an announcement is often not the home machine and no host writes to another host's disk.

### Disambiguation: when to use `patch_wake_me` vs `patch_job_*`

Both fire on a delay/schedule. The agent picks based on destination:

- Same conversation ("remind me to check this in 5 minutes", "nag me to go to bed every 10 min until I do") → `patch_wake_me` (`02-daemon.md` § Self-wake). Durable, adaptive, self-terminating. (Claude Code's `CronCreate` is disallowed here — it can't fire in the host; see `principles.md` § Tool ownership.)
- Different chat or new chat, indefinite ("every weekday 7am, start a fresh bus-watch chat", "every Sunday morning, write the newsletter") → `patch_job_create` with a `cron` trigger.
- External event (webhook arrival, Todoist task) → `patch_job_create` — the agent's own tools don't handle these.

The tool descriptions for `patch_wake_me` / `patch_job_create` lead with this rule so the agent reaches for the right one without prompting.

### Disambiguation: in-session vs `patch_delegate` vs `patch_spawn` vs `patch_send_to`

Four ways to get other work done, by lifetime and visibility:

- In-session (the agent's own file editing, search, bash, web) — anything the agent can do inside this turn without the work outliving it. `Agent`/`Task`/`Workflow` (native sub-agent dispatch) are disallowed (`principles.md` § Tool ownership, `02-daemon.md` § Native subagent dispatch): a sub-agent they launch runs inside THIS turn's process, so a restart kills it and the resumed turn has no way back to its work.
- `patch_delegate({ prompt, model?, folder? })` — a sub-task (patch's Task/Agent: `wait: true` blocks for the result, `disallowedTools` limits its capabilities, `patch_delegate_send` continues it) that should run on its own and hand its result back here, without becoming a chat the user has to deal with: "research X and report back," "do this chunk of the larger job while I carry on." Durable (outlives the turn and a host restart) and invisible — not in the user's sidebar, search, or notifications; the only way into it is this chat's own tool-call row. Use this, never `patch_spawn`, for anything the user never needs to see as its own chat.
- `patch_spawn(daemonId, folder, model?, prompt?)` — when the user wants a new, persistent, user-visible chat as an artifact. Use for: "make me an app for X" → spawn a chat in a new folder; "write the weekly newsletter" → spawn a chat that produces output the user can revisit.
- `patch_send_to(chatId, message)` — when an existing chat's agent should receive a message and process it as if from the human user. The agent reads, responds, possibly acts. Use for: "tell agent two to use option B," "remind the bus-watcher to check again." Not for announcements or any user-facing message — those are `patch_notify`.

The defining question: can this finish inside my own turn (in-session), should it run independently and report back to ME (`patch_delegate`), does it need to become its own chat the user can open (`patch_spawn`), or does an existing chat need a message (`patch_send_to`)?

All chats get the same tool surface — including `patch_notify` (covered in `09-notifications.md`) plus the cross-chat and job tools. We considered scoping the toolset by chat type and decided it added wiring for negligible benefit; nothing in a regular chat's prompt steers it toward `patch_spawn`. The special threads are special because of ingress (voice-device audio, voice queue) and role (defined in their `CLAUDE.md`), not because of restricted tools.

## Reply routing — channel-aware, not agent-decided

Direct replies to a user turn route automatically back to the source channel. The agent does not decide; the host enforces the mapping.

| User turn arrives via                            | Direct reply routes to                     |
| ------------------------------------------------ | ------------------------------------------ |
| Manager voice queue (tap-to-talk in app)         | Voice in the same surface (audio response) |
| Manager text input (web/mobile composer)         | Text in the same surface                   |
| Speakers — physical voice device with `deviceId` | TTS on the originating device              |

Web/mobile composer is disabled for Speakers (see Composer policy below) so this row is omitted for it.

This is the equivalent of "reply-all goes to the sender" in email. It removes the failure mode where the agent forgets to call `patch_notify` after handling a turn and the user gets silent radio.

`patch_notify` remains for asynchronous outreach — when an agent (in any chat, including these two) wants to push something that isn't a direct reply (bus reminder fired 20 minutes later, build-failed alert, scheduled job result). There the agent picks both channel and `deviceId` (for `speakers`), because a deliberate interrupt is exactly the moment when channel/device choice matters.

## Manager failover

When the home host has been offline for two minutes and another host is online, the server asks that host to run the Manager for the time being It sends `host.manager_adopt` with the recent conversation from the server's own copy (the last `managerContextWindow` messages) and the seq the Manager carries on from, so the thread keeps one sequence across hosts. The stand-in creates the thread, and gives the conversation to the Manager once, with its next message, as a disclosed system reminder. From then on the server takes the Manager's and Speakers' events from the stand-in and runs the sweep there; frames from the home host are ignored.

When the home host returns, the server sends `host.manager_release` to the stand-in and, if anything was said meanwhile, a `host.manager_adopt` to the home host with that stretch and the seq to continue from. A replay of the Manager is answered by the home host from its own log and the server adds the stretch that log is missing. A host that was away when it was told is told again when it attaches, and acts on each takeover once (`epoch`). If the stand-in goes offline another host is chosen. With no other host online the Manager stays unavailable, readable from the server's copy, and takes messages for when the home host is back.

## Disabled

Special threads hold fixed sidebar slots and have no "off the home screen" state to hold — `archive`/`snooze`/`delete` are all refused for them (enforced server-side and host-side, not just by the UI hiding the affordance; a hand-crafted CLI/API call is refused the same way). Instead each of the two can be individually **disabled**: a chat-level `disabled` flag (`chat.state`, spec/03), toggled from the header's Power icon (replacing Archive in that slot for a special thread) or `patch chats disable/enable <id>`.

Disabling stops the thread's own ingress — the sweep drops candidates for a disabled Manager rather than banking them for later delivery, and Speakers stops delivering inbound turns — without touching anything else: the chat still exists, is still openable, and its history is untouched. The composer shows read-only with a note to re-enable from the header, and the sidebar row/Channels entry greys out (the same visual treatment archived rows get).

This exists because archiving used to be the only affordance offered for "I don't want this running right now," and there was nothing stopping it from being applied to a special thread — which does not mean what it means for a regular chat: the (now-removed) per-event watch kept delivering turns into an archived Manager regardless, since nothing gated on its own status.

## Session rotation

A special thread's session grows forever by design (§ What they share) — SDK auto-compaction fires when the model's own context window happens to fill, which is not a policy, just wherever a boundary happens to land. Manager alone sat on `claude-opus-5` for 18 days without a single compaction after a model change, running roughly 750k cached tokens a turn (up from ~170k — where it HAD compacted three times — under the previous model).

Account settings (`specialThreadModel`, `rotationEnabled`, `rotationTime`, `01-server.md` § Responsibilities) govern this: `rotationTime` (`HH:MM`, local) is when a due rotation runs, once per calendar day per thread, skipping a thread that's disabled or mid-turn (retried the following day, not immediately). At the scheduled time:

1. The outgoing session is asked — resumed, not re-fed from scratch, so it rides its own prompt cache — to write a short handoff: standing facts, anything open, preferences learned. Not a recap.
2. A `system` `chat.message` records the boundary ("Session rotated · digest carried over"), same arrangement a compaction boundary uses (`02-daemon.md` § Context compression), so it replays with the rest of the chat.
3. The session is retired (`claudeSessionId` cleared) and a fresh one starts on `specialThreadModel`, seeded with the digest as its first turn.

The chat's own id (`thread_manager`, etc.) never changes — only the session underneath it — so pinning, ingress wiring and sidebar identity are untouched. A digest generation failure skips that day's rotation rather than starting a fresh session with nothing carried over (NO FALLBACK, `12-...md`).

## Sidebar placement

- Manager sits pinned at the top of the sidebar — it is the only special thread the user actively drives from the surface they're on.
- Speakers lives in a small Channels section near the bottom of the sidebar, collapsed by default. It auto-expands or surfaces a small badge when there is unread activity.
- The Channels section is not a folder — it cannot contain regular chats. It is a fixed slot for the passive-mirror special.

This reflects how often each is opened from web/desktop. Manager is conversational; Speakers is mostly observed.

## Smart-home control from a desk

The Speakers thread is not the place to type smart-home commands from a desk — its composer is disabled.

For desk-side HA control, the user creates a regular chat in their own folder (e.g. `~/projects/home-assistant/`) with HA REST available as a tool, and pins it to the sidebar (see `04-chats-and-folders.md` § Pinning). One pinned HA chat, used continuously — `lights off`, `kitchen scene`, `why didn't the porch automation fire`. No new chat per command, full record of every command.

Patch ships an HA `CLAUDE.md` template the user can copy into their HA chat folder if they want a starting point ("be brief, you are a control surface"). Patch does not own the HA chat — the user does.

## Manager thread

- Ingress: web app + phone app. Dedicated "Manager" entry in the sidebar, plus the sweep below.
- Voice: supports interactive voice via tap-to-talk in the app. Uses the focus-follow voice model — when you focus a different chat in the app, voice routes there instead. See `07-voice-app.md`.
- Purpose: your primary way to ask "what's going on?", kick off work, stitch chats together, and the one place to talk to when running several simple chats at once. Does stuff on your behalf — creates jobs (`patch_job_create`), spawns chats, triggers notifications.

### The sweep

PURPOSE: chats stop and ask "done half of it, shall I do the next bit?" and someone has to be the monkey pressing the button. The sweep pokes those on. It replaces an earlier design — a watcher that ran a full Manager turn for every chat event — which worked but did not scale: the Manager thread it fed became a ~5,000-message conversation too costly to run at all, and most of those events needed no judgement ("this chat went idle" is not news). The sweep is a periodic, gated check instead: it runs far less often, it is not a turn in the Manager's own conversation, and a run with nothing to act on costs nothing.

**Gate.** A sweep only runs if something changed since the last one:

| Changed condition                                                    | Edge                      |
| -------------------------------------------------------------------- | ------------------------- |
| a chat settled (went idle from running, not stopped by the user)     | `settled`                 |
| a chat has been running with no new output for the stalled threshold | `stalled`                 |
| a monitor / `patch_watch` / background task ended                    | `task-ended`              |
| a job run failed                                                     | `job-failed`              |
| a permission or `AskUserQuestion` is waiting                         | `permission` / `question` |

`stalled` is raised once per quiet stretch: a chat still running is raised again only after another full stalled threshold since the last time, so one long step is not nudged on every tick. A chat that holds a nudge or wake the sweep sent, which has not yet been delivered or acted on, is not a candidate for `stalled` or `settled` until it has been; a permission or question still comes through.

Nothing changed since the last sweep means no model call, full stop — the gate is checked before anything else, and a tick with an empty pending set returns immediately. `stalled` exists because a chat can go quiet for reasons that look identical from the outside — genuinely done, or stuck — and "running with no output for N minutes" may need a wake-up even though it "expected" to stop on its own.

**Triggers.** Three ways a sweep is asked for:

- **Interval.** Every `sweepIntervalMinutes` (default 30), still subject to the gate above.
- **Event-woken.** A `task-ended` or `job-failed` edge also wakes a sweep early, rather than waiting out the rest of the interval — but never sooner than 2 minutes after the previous early wake or the previous sweep, so a burst of endings doesn't fire a sweep per event. Still gated: the early wake only matters if something is actually pending.
- **Check now.** A button in the Manager view (`14-design-web.md` § Manager view), and `patch threads sweep-now` on the CLI (`17-cli.md`). Forces an attempt immediately, bypassing the interval — but NOT the gate: nothing pending is still no model call, reported back as "nothing changed."

**The run.** A due sweep is a fresh, short, isolated decision — a one-shot model call on the account's home host, not a turn in the Manager's own conversation and not visible in its transcript. It is handed a compact digest: the chats that changed, each with its host/folder, how long idle, and its last `sweepMessagesPerChat` (default 3) messages. For each changed chat it picks exactly one action:

- **nudge** — the chat is idle and plainly just asking permission to continue ("shall I do the next part?"). Delivered as an ordinary machine turn into that chat (the same mechanism `patch_send_to` uses).
- **wake** — the chat has stalled; a short message checking it's still working, delivered the same way.
- **flag** — worth one line to the user, but not something the sweep can act on itself: a job failure, or anything blocked on a person. Written as a single quiet line on the Manager thread's own log — never a turn, so it never reaches the Manager's own model context (bounded context below drops `system`-role entries from reconstruction the same way a session-rotation boundary already does).
- **leave** — nothing to do.

It never answers a real question and never approves a tool permission, and this is enforced in code, not merely asked for in the prompt: a candidate carrying the `permission` or `question` edge is downgraded to `flag` regardless of what the decision call returns.

A nudge or wake is only delivered to a chat that is idle. A chat with a turn running or a queue draining is left alone (recorded as `leave`): the message would only park in its queue until the turn ends, stale by then, and each later sweep would stack another behind it. The next sweep reconsiders once the chat settles. Enforced in code in `deliverSweepMessage`.

**Settings** (Manager settings page, `14-design-web.md` § `/settings` details): sweep enabled, interval, stalled threshold, messages per chat, Manager context window (below), the sweep prompt, and the model it runs on (default a mid-size model — cheap enough to run often, capable enough to read intent off a handful of short transcripts). The prompt is editable in Settings as plain text, with a Reset to default, the same pattern as the Patch tools prompt (`14-design-web.md` § Agent behavior) — a built-in default shown and editable rather than a hidden directive (`principles.md` § No system-prompt injection).

**Visible.** The Manager view shows a slim line — "Last sweep 14:30 · nudged 2 · flagged 1" — expandable to what it did to which chat, with links to open them. Sweep runs are also recorded and listed like job runs (`08-triggers-and-jobs.md` § Logs).

### Manager conversation — bounded context

The Manager thread's own history still grows forever in the log, exactly as every special thread's does (§ What they share) — but the MODEL backing it only ever sees the last `managerContextWindow` messages (default 40) of its own conversation, not the whole thing. Once the track grows past that window, the next turn reconstructs a fresh native session from the trailing window alone (`nativeReconstruct`, the same mechanism a provider switch or a session rotation already uses to seed a session from a track), rather than resuming the ever-growing one. History is never touched by this — only which native session `claudeSessionId` points at. Sweep traffic never reaches the Manager's conversation at all (above), so this budget is spent entirely on real exchanges and flags.

This exists for the same reason session rotation does (§ Session rotation above) — Manager once ran ~750k cached tokens a turn for 18 days without a single auto-compaction — but is a tighter, continuous bound rather than a once-a-day reset: bounded context trims every turn once the window is exceeded; rotation still runs on its own schedule underneath it for the full-session digest-and-restart case.

## Speakers thread

> Hardware coupling: patch ships with at least one flashed HA Voice PE unit. The Speakers thread, the smart-home control path, the `speakers` channel on `patch_notify`, and the kitchen-listening pill all depend on one being present. Adding more devices is additive — same firmware, new `deviceId`. See `16-voice-device.md`.

> Naming note: "Speakers" = the special thread for the physical voice devices (kitchen, bedroom, etc — the HA Voice PE units). Distinct from voice mode, which is the per-chat action of opening a tap-to-talk session for a regular chat (invoked via the mic icon in any chat's header — no text label, just the icon).

- Ingress: one or more standalone voice devices (HA Voice Preview Edition re-flashed with patch's custom firmware — see `16-voice-device.md`). Audio streams from device to the host's audio WSS; host runs Whisper STT and Kokoro TTS locally. No third-party voice service.
- Voice: yes, full bidirectional. Audio is the only ingress for this thread.
- Web composer: disabled (read-only transcript).
- Device awareness: each inbound audio session carries the originating `deviceId`, so the agent knows which device the user is on (kitchen, bedroom, etc.) and can shape responses accordingly.
- Cross-chat tools: yes. Same toolset as every chat — can spawn new chats ("hey make me an app for X"), send messages into existing ones, create jobs, etc.
- Purpose: hands-free ingress wherever a voice device is. Short commands, status checks, dispatch ("plan my bus route", "what's agent two doing", "remind me when the bus is leaving").
- Cross-chat queries done locally, not delegated. When the user asks "how are my jobs going", the speakers thread calls `patch_list_chats` and `patch_peek` itself — it does not bounce the question through Manager. Patch is glue, not a hierarchy; agents handle their own questions and only spawn sub-agents (via Claude Code's `Task` tool) when they need help.
- Smart-home control from speakers: this thread can call Home Assistant's REST API as a tool, since voice utterances often include smart-home intents ("turn off the kitchen lights"). The agent decides whether an utterance is a smart-home command, a question, a dispatch, or nonsense. See `16-voice-device.md` § Loss of HA Assist. For desk-side HA work — see Smart-home control from a desk above.

## Why keep them separate

If speakers inbound landed in the Manager thread, the context would get noisy — crosstalk from a different channel would confuse the agent and the human reader. Each ingress gets its own dedicated history, but both share the tool surface.

## Voice-note shortcuts on every chat row

Every chat row in the sidebar (web) and chat list (mobile) carries a tap-and-hold mic affordance — see `14-design-web.md` § Row tools and `15-design-mobile.md` § Row tools (mobile gestures). Holding it opens the voice-note overlay (`07-voice-app.md` § Voice-input modes), targeted at that row's chat. Releasing or pressing `⏎` sends a single user turn to the chat without opening it. This is the desk-side counterpart to walking into a room and saying "hey kitchen, lights off" to a Speakers device — same one-shot ergonomic, different ingress.

The Manager row is the most-used target. Because it is the primary voice affordance, the Manager row's mic renders as a prominent, enlarged, accent-tinted control (the `mic-btn--manager` variant) sitting on the right of the row and always visible — not the small grey hover-only mic used on ordinary rows. The menu-bar surface (`05-surfaces.md` § Menu-bar (system tray) surface) provides a global hotkey that fires the same overlay even when the patch app is closed.
