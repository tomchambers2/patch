# Mobile App Design

Android-native via Expo / React Native. Code shared with the web app where practical (chat stream rendering, wire-protocol client, voice bridge).

Reference mocks: `design/mobile-hi-fi.html`, `design/mobile-hi-fi-all-screens.html`. Visual system identical to web (see `14-design-web.md` § Visual system); § Visual language below is how the phone carries it.

Visual language. The phone reads like the desktop app: soft, calm and warm — never a terminal. It shares the desktop's palette, radii and type rather than approximating them.

- Colour. Both palettes (light and dark) are the desktop's tokens, colour for colour: warm paper ground, white raised cards in light, the same leaf-green accent, ink ramp, hairlines, tints and state hues. A test pairs every shared token with `packages/web/src/index.css` in both schemes, so the two cannot drift apart. The accent is used sparingly: tints and soft edges for selection (an active row, a selected chip, the user bubble, the Manager card) and a solid fill only for a primary action (Send, a primary button, New chat).
- Type. Inter for everything a person reads (regular, medium for names and labels, semibold for emphasis — real faces, never a synthesised bold). Upright Fraunces for screen, chat, sheet and modal titles, as desktop's page and chat titles. Italic Fraunces for the `patch` wordmark and empty-state titles only. The shared type styles (`typography` in `src/lib/theme.ts`: screen title, title, section header, body, row title, label, secondary, meta, code) are what screens use, so the same kind of text looks the same everywhere.
- Section headers are sentence case in the body face — the label's own words, never upper-cased or letter-spaced.
- Monospace is for code only: fenced and inline code, a tool call's raw arguments and background-task blocks, diffs, the file editor, the terminal, shell/script and JSON input, and a command the user copies. Folder crumbs, paths, ids, timestamps, counts, status words, host names, model names and settings values are body text. A test fails on a mono face named anywhere outside an allow-list of code-rendering components.
- Surfaces. Cards, rows and bars have desktop's radii (10 for rows, fields and bars; 16 for cards, bubbles and sheets; pill for chips, status pills and round actions) and a soft hairline edge rather than a drawn box or a drop shadow. Content has room: card padding and section spacing come from the upper steps of the spacing scale.

Spacing. Padding, margin and gap follow one 8px-based scale (`4 · 8 · 12 · 16 · 24 · 32 · 48`); a screen uses scale steps throughout. Every screen is held to the same scale so the app reads as one system — no one-off insets.

Safe area (top). The app draws its own header (there is no native navigation bar — `headerShown` is off), so every screen must inset its top content below the status bar / notch. The first painted element (a screen title, a section header, a back-bar) sits below the device's top safe-area inset, with the normal `space.*` gap added on top of that inset, clear of the status bar. The inset is counted once, by that wrapper: a screen's own top bar (chat detail, Jobs, the job editor) adds only its small normal padding (`space.sm`) on top, never a second inset's worth of spacing. Use the top inset from `react-native-safe-area-context` (a single shared screen wrapper — `app/_layout.tsx`'s `SafeAreaView`), applied uniformly so no screen title ever collides with the clock/battery row. The Chats tab's slim header (§ Chats tab → Header) is its first painted element and its gap below the inset.

Minimum text size. `textMin` (13, `src/lib/theme.ts`) is the floor for every string the app draws, however secondary — the same number web's `--text-min` holds (`14-design-web.md` § Legibility), so the two surfaces read alike. It is a scale value like `space` and `radii`: a screen writes `fontSize: textMin`, never a bare literal below it. Enforced by a test that scans every screen and component and fails on a sub-floor literal; an exception needs an allow-list entry and a comment at the call site saying why. There are currently none.

Display font. Titles render in the upright Fraunces display face (`fonts.display`), the wordmark in italic Fraunces (`fonts.brand`); `fontStyle: 'italic'` on a default font is a bug. Fonts are never blocked on: the app paints on the platform default face from the first frame and the custom faces apply as soon as they load. A font set that fails to load raises a visible error rather than leaving the app silently on the default face.

Dark mode. The app follows the OS colour scheme (`useColorScheme()`) — no in-app toggle. Two full palettes ship, light and dark, sharing the same token names; dark is a warm translation of the leaf/cream identity (near-black warm-brown paper, cream ink, the leaf accent muted to about two-thirds chroma so a fill reads as chosen colour rather than neon, carrying dark on-accent button text), not an inversion. Every screen and component reads the active palette via `useTheme()` at the top of render — never the static light palette — so the whole app, Jobs and the job editor included, renders in one scheme; a test fails on any screen or component that imports the static palette for styling. Text and icons drawn on a solid accent fill (a leaf button, a red or amber chip) use the `onAccent` token rather than a literal white, so they stay legible on the lifted dark accents. The few colours that are the same in both schemes by design — text on the near-black scrim of the voice overlays, drop shadows, the camera backdrop, the image-viewer ground — are named scheme-independent constants (`fixed`), not palette tokens. Every dark token is present and distinct from its light counterpart, so every screen resolves a real colour. The status bar adapts with the scheme (light glyphs on dark paper, dark on light). Markdown tables in the transcript meet web's table legibility rules (`14-design-web.md` § Theming → Tables), measured against the page an assistant reply sits on.

## Pairing and the server route

No server address is built into the app. A phone with no credential shows the pairing screen, whose camera reads the `patch-pair://` code another surface or `patch-server pair` shows (`05-surfaces.md` § Canonical QR payload). The code says where the server is: a direct address, or a relay and the server's key. Pairing aims at it first and keeps it as this phone's route only once pairing has worked; a failed pairing puts back the route it had.

A route through a relay (`10-auth.md` § Relay) changes nothing the user sees. Requests and sockets addressed to the route go through the encrypted session; everything else goes to the network. A file the server serves — an attachment image, an artifact — is fetched through the session into the phone's cache when a native view or the viewer needs an address it can open, and the viewer offers no "Open in browser", which has nothing to open. A phone on a relayed route takes updates over the air only; the Download APK action is not offered, since there is no address to download it from. Settings shows the route (the host, or the relay it goes through) and Diagnose reports it.

## Navigation shell

Bottom tabs (5), in order:

- Chats — default landing. Chat list (same shape as web sidebar, vertically stacked).
- Jobs — the job list (§ Jobs screen).
- New chat — the true centre of the bar (third of five). Opens the new chat flow (§ New chat flow). Raised green button so the affordance is obvious for one-handed use, horizontally centred within its own tab cell (a `flex:1` cell with centre alignment around the fixed-size button).
- Voice — immediately right of New chat, direct into the Manager thread for tap-to-talk. A regular tab like its neighbours (icon + label), but its button still carries the hold-to-talk gesture: tap-and-hold sends a quick voice note, a plain tap opens the Manager thread.
- Settings — the same sections as web's Settings page, plus Secrets (§ Settings tab).

Jobs are reached from their own bottom tab, not from a row on the Settings page: a job is a top-level thing you check on, not a preference. Each row on the Jobs tab opens a full editor sub-screen (§ Job editor). The Settings page carries no Jobs row — a second door onto the same screen. Notifications are ephemeral (see `09-notifications.md` § Notifications are ephemeral).

A screen's own back arrow returns to the screen the user was on before it, wherever that was. When there is nothing beneath it — a launcher shortcut or `patch://` link opened on a cold start mounts its screen alone — the arrow goes to the screen's parent instead of doing nothing: the Chats tab for a chat or the new-chat screen, the Jobs tab for the job editor, the Settings tab for a settings page, the chat for its Tools page, the host's page for its files and terminal.

## Chats tab

Same conceptual shape as the web sidebar (see `14-design-web.md` § Sidebar), rendered as a single full-width column under a slim header.

Directly under the header sits the view dropdown (§ View dropdown) — the phone's equivalent of the sidebar's own view switch (`14-design-web.md` § Sidebar §1b), as its own row: the phone has no room to put it beside a search field the way the sidebar does, and search stays reached through the header's own search button (§ Search) rather than sharing this row. Its `All` option is the `Chats` view described below; `Batch` swaps the column for the batch review view (§ Batch view).

The `Chats` view itself:

1. Manager — its own card at the top of the list, directly under the header with no section label of its own, drawn unlike any chat row: an avatar (the Manager glyph on a leaf-green disc), the name, the last message (up to two lines), and the Manager's status on the right of the name (`Working`, `Waiting on you`, `New reply`, `Idle` — words, not the chat-row status glyph). Along the bottom of the card, two buttons: Call and Hands-free, which start exactly the sessions the Manager chat's top bar does (§ Voice tab (Manager)) without opening the thread first. The third control, Voice note, is the card's own tap-and-hold gesture rather than a third button — tap anywhere else on the card opens the Manager thread; tap-and-hold triggers a voice note (same overlay as web — see `07-voice-app.md` § Overlay surfaces). All three — the two buttons and the hold gesture — are bound to the Manager's own `chatId`, never to whichever chat is open elsewhere in the app, matching the web sidebar's Manager block (`14-design-web.md` § Sidebar item 2). No pin marker — the slot is fixed, not pinned.
2. Pinned chats — any user-pinned regular chat. Pin marker visible on each row; the row's ⋯ menu (or long-press) → Unpin. Unpin must be reachable directly from the chat list, not only from chat detail.
3. Folders — the folder label label followed by chat rows. Same row layout as web: status badge (left), name + preview (middle), ⋯ row-actions button (right). Folder and row order follow `14-design-web.md` § Sidebar ordering. The preview settles on load: when the host replays a burst of events for a chat, the row shows its latest settled preview rather than flicking through every intermediate message. Row actions via the ⋯ menu (or long-press).
4. Channels — bordered section above Archived. Speakers, read-only. Expanded by default (a collapsed section reads as "hidden/broken" — the user should see their channels without hunting for a disclosure). It stays collapsible, but the initial state is open. When there are no channels to show, the expanded section renders a proper empty state (§ Empty states — "No channels yet").
5. Hidden — single row carrying a muted count, collapsed by default. Lists the chats running out of the active list (`04-chats-and-folders.md` § Hidden), newest first, each an ordinary chat row; Show is in Pin's place on the row's swipe tray and on its actions menu (§ Row tools). A hidden chat is drawn here and nowhere else — not in Pinned, its folder or Snoozed — and an archived chat that keeps the flag is drawn in Archived. Like Archived, hidden chats are not in the cold-start chat list: the count is the server's total, no number is drawn until it has answered, and opening the section fetches the list, which `chat.state` then keeps live.
6. Snoozed — single row carrying a muted count of the snoozed chats, collapsed by default. Lists the chats snoozed into the future (`04-chats-and-folders.md` § Snooze), each an ordinary chat row whose right-hand slot shows its wake time compactly — `14:00` today, a bare weekday within the coming week, day and month beyond — with no extra line under it; Unsnooze is on the row's swipe tray and actions menu (§ Row tools). A snoozed chat is drawn here and nowhere else: it leaves the Pinned and folder sections until it wakes, and returns to them on its own the moment its wake time passes. When nothing is snoozed the expanded section shows the snooze empty state.
7. Archived — single row carrying a muted count, collapsed by default. The count is the server's total (`04-chats-and-folders.md` § Section counts) — archived chats are not in the cold-start chat list, so the phone cannot measure the section itself; no number is drawn until the server has answered. Opening the section fetches the archived chats and lists them newest first.

Each section's open/closed state is remembered on the device across launches; the defaults above apply only until the user first toggles it.

### Header

One fixed row, 44dp tall, at the top of the Chats tab only: the `patch` wordmark (display face, leaf green) with a small connection dot riding its ascender on the left, and a search button (magnifier icon) on the right. The dot reflects the WS link only (§ Offline / error states): green connected, amber reconnecting, red offline; while the first connection is still being made there is no dot. The header is the list's top gap — the Manager row sits directly under it — so it adds no vertical space of its own.

### Search

Tapping the search button swaps the header's content for a search field, labelled simply "Search chats", and a close button; the header keeps its height. The search covers every chat on every host, by name and by what was said (`04-chats-and-folders.md` § Search).

- A one-character query filters the list in place, instantly and locally: every section at once — Manager, pinned, folders, channels, hidden, snoozed and archived, collapsed or not — case-insensitively on name and preview. Sections keep their order and their rows' order, a section with no match drops out, and the section headers become plain labels without their toggles or counts. Opening search fetches the hidden and archived chats (as opening either section does) so they can be matched.
- From two characters the list is replaced by results. The request goes out once typing pauses (300 ms) and only the answer to the latest query is drawn; until it lands, the local matches are shown the same way under `Searching…`, and the server's answer then replaces them.
- A result row, on the chat-row card: the chat's title with the matched terms marked, the snippet with its terms marked (a user message reads `You:` first), and a muted line — host · where the chat lives (Manager, Channels, Pinned, the project name, Hidden, Snoozed or Archived) · `Automation` for a job-created chat · how long ago, and how many more messages matched when there are others. Tapping it opens the chat at the matched message (§ Chat detail).
- No hits shows the empty-search state. A failed request shows `Search failed: <reason>` in the list, not only a toast. `More results` at the foot loads the next page.
- Every host the answer says was not searched gets its own line under the results, hits or no hits: `<host> offline — not searched`, `<host> didn't answer — not searched`, or `<host>: <reason>`.

Clearing the field restores the normal list; closing the search also drops the query.

### Status badges

Same seven-state badge system as web (see `14-design-web.md` § Status badges), slightly larger to accommodate touch, and the same precedence order (a pending permission or declared question outranks an error, which outranks working, which outranks unread, which outranks `background`, which outranks `monitoring`, which outranks `read`):

- `working` — flashing solid green dot, no ring.
- `permission` — orange dot with thick orange target ring, same size as `done`.
- `errored` — a drawn triangle-alert glyph in the danger red, same as web — the chat's last turn failed.
- `done` (unread) — green dot with thick green target ring.
- `background` — a static (non-spinning) terminal glyph in muted grey — no turn is in flight, but a background command or sub-agent the chat launched is still running.
- `monitoring` — a static clock glyph in the same muted grey — no turn is in flight; the agent has a self-wake armed and will check back on its own.
- `read` — small grey ✓ tick; row name/preview subtly greyed.

### View dropdown

One pill + pop-up (`All chats ▾`), the same shape as every other dropdown on the phone (a pill naming the current choice opening a dismissible option list — see § New chat flow → folder/model pickers): `All` · `Unread` · `Working` · `Waiting on you` · `Failed` · `Batch`. Picking an option is exclusive — always exactly one of the six. The trigger reads `All chats` at rest and the chosen option's own label otherwise. The choice persists on the device across launches, the same as the Chats tab's own collapsible sections (§ Chats tab).

- `All` — nothing is filtered; the `Chats` view described above.
- `Unread` — filters the Chats view to Pinned + Folders only — Channels, Snoozed and Archived hide entirely — down to rows that need you (`done` or `permission`, the latter also covering a declared `question`; § Status badges). Opening one of those rows marks it read, which would ordinarily drop it out of the filter; instead it stays in the filtered list, greyed exactly as any other read row, until you navigate to a DIFFERENT chat — that navigation is what releases it, and only one row is ever held this way at a time. This lets the queue be cleared one at a time: reading a chat and moving to the next removes the one just left, rather than the row vanishing under your thumb the instant you tap it. Within the filtered list, rows queue FIFO — oldest-waiting first, `permission` rows leading — rather than the Chats view's normal order (`14-design-web.md` § Sidebar ordering), so a row that updates again while still in the queue rejoins the back of it instead of jumping back to the front. With nothing left in the queue the list shows the same empty-state pattern as everywhere else (§ Empty states): "Nothing needs attention" — "You're all caught up."
- `Working` / `Waiting on you` / `Failed` — narrows Pinned + Folders to rows in that one state (§ Status badges), leaving Channels, Hidden, Snoozed and Archived showing: these ask "what's in this state", not "what needs me", so the rest of the list stays reachable. Driven off the same badge precedence the row's own glyph uses, so what you filter for and what you see on the row can never disagree.
- `Batch` — swaps the column for the batch review view (§ Batch view); the option carries the same non-zero member-count badge web's own dropdown shows.

### Batch view

The view dropdown's `Batch` option (§ View dropdown) swaps the column for the batch review view — same account-wide batch, held server-side, as web (`14-design-web.md` § Batch mode); the phone and the sidebar can never disagree about what is in it or whether it has checked in. With no batch running, the view's whole content is a `Batch` button offering the same check-in choice web does: `15 min` / `20 min` / `30 min` (default 20), or `When all done` (capped at 30 min). Membership is automatic — every chat started or messaged into while a batch is running joins it — not curated through a row toggle. A batch spans hosts.

Before check-in, the view shows the check-in time and the member rows (the same chat-row component the Chats view uses, but marked only "waiting" — no status badge) with a remove (×) control beside each, plus a `Check in now` control. Removing only drops the chat from the batch; the chat itself, and its place in the Chats view, is untouched.

Check-in happens at the first of: the chosen time elapsing, every member finishing (`When all done` only), or `Check in now`. The first two fire ONE push notification, `Batch ready: N done, M still running` (`09-notifications.md` § Chat completion); `Check in now` does not. From check-in on, the view lists members by their real status badge instead of "waiting", done first.

The batch ends once every member ready at check-in (or since) has been opened — from anywhere, not only this view. Members still running when it ends roll into the next batch, started the same way.

Tapping the check-in push notification lands on the batch view: it sets the view dropdown to `Batch` and opens the Chats tab if another screen was showing, exactly as a message notification opens its source chat.

### Row tools

Each chat row carries a small ⋯ (kebab) affordance on its right. Tapping it — or long-pressing anywhere on the row — opens a bottom-sheet actions menu. A row also swipes open from either edge, revealing a three-button tray (Pin, Snooze, Archive — Show in Pin's place on a hidden chat) that calls the exact same functions the sheet's own items do — so a swipe and a sheet tap always agree. The swipe tray is additive: Delete and "Send voice note" stay sheet-only, and the kebab/long-press sheet remains the one place every action is reachable without a gesture.

The row-actions menu contains, top to bottom — the tray's three, in the tray's order, mirroring the web sidebar row's own tools order (`14-design-web.md` § Row tools — archive · pin · mic):

- Show chat — on a hidden chat only (`04-chats-and-folders.md` § Hidden): moves it into the active list without sending it anything.
- Pin chat / Unpin chat — toggles pin; usable directly from the list.
- Snooze chat — replaces the menu with the wake-time presets of `04-chats-and-folders.md` § Snooze; picking one snoozes the chat and closes the sheet. There is no custom date/time entry on the phone, so the presets are the whole list. On an already-snoozed row the item reads Unsnooze chat and clears the snooze in one tap, with no preset list in between. Absent for special threads, which cannot be snoozed.
- Archive — archives immediately; on an already-archived row this reads Unarchive and restores it.
- Send voice note — opens the voice-note overlay.
- Delete chat (red, destructive) — last.

Tap-and-hold on the Voice bottom tab opens a global voice-note overlay targeting Manager (the mobile analogue of the desktop menu-bar global hotkey).

## Chat detail

Full-screen stream. Top bar carries:

- Back arrow (left).
- Folder name and host name (body face, ink-3, small) above the chat name (upright Fraunces), as `folder · host` like web's crumb, each segment drawn only when known — the folder as its basename, the host as its machine name, all on one line, on the same rule as the folder pickers (§ New chat flow) and web's crumb (`14-design-web.md` §8). The top bar shares its width with the pills and buttons to its right, so a full path wrapped here reduces the name beside it to a letter. Special threads (Manager / Speakers) show no folder crumb: their fixed label is the title, and the crumb above it would only repeat the same word.
- `waiting on you` orange pill when in `permission` state.
- Call button (phone icon) on the right — starts a sustained voice call for this chat (`07-voice-app.md` § Voice-input modes mode 2/3). This button and the ⋯ menu's Call (the same action) are the only places a voice call is started on mobile; the composer mic dictates. There is no Tools icon in the header — Tools lives in the ⋯ menu.
- `⋯` kebab on the right — opens a compact anchored dropdown menu positioned at the kebab (top-right), NOT a centre-screen stacked-button alert dialog, in this order: New chat / Call / Tools / Show chat (a hidden chat only) / Pin chat / Snooze chat / Archive chat / Move to… / Disable / Delete chat — each only where it applies, Delete last, in red. Move to… pushes a page choosing the machine, then the folder there (`04-chats-and-folders.md` § Moving a chat to another host). (Files and Open editor are not on the phone, and neither is the web/desktop header's own merged Editor control.)
  - New chat opens the new-chat screen (§ New chat flow) already set to THIS chat's host and folder, because "another one here" is what it is for. It is still type-first: nothing is created until the first send. A chat whose host is not yet known (not yet spawned) says so in an error toast rather than guessing. From a special thread — whose folder is its private working dir, not a project — it opens the new-chat screen on its usual default instead.
  - Call is the header phone button's action.
  - Tools pushes the chat's Tools page (below).
  - Snooze opens the same preset sheet the row tools use, and reads Unsnooze chat while the chat is snoozed. Archive calls the very function the Chats-tab row tools call (same store write, same REST call) and then navigates back to the chat list, since the chat has left the active list; an archived chat reads Unarchive chat, which restores it and keeps the user in the chat.
  - Disable (special threads only) is the special-thread off switch (`06-threads-manager-speakers.md` § Disabled), the same `POST /api/chats/:id/disable` web uses; a disabled thread reads Enable. Optimistic, reverting with an error toast if refused.
  - Special threads (Manager / Speakers) show the ⋯ too, carrying only what applies: New chat, Call, Tools and Disable — never Pin, Snooze, Archive or Delete (fixed slots). The read-only mirror (Speakers) also drops Call and Tools: nothing sent from it reaches a model.
  - Tapping outside dismisses it. (A true-native `ConnectionService`-style menu module was incompatible with the RN 0.76 / Kotlin 1.9.24 toolchain, so this is a themed in-app dropdown that reads as a proper menu — the point is the anchored, tidy presentation.) The raw wire event log is not reachable from the chat view on mobile — it is a developer surface, available via the CLI (`patch chats history` / `patch doctor`; see `12-error-and-offline.md` § Observability), not a chat affordance.

Tools page. ⋯ → Tools pushes a full-screen page (`/chats/<chatId>/tools`) with a back arrow and the title `Tools` — the phone's equivalent of desktop's Tools panel. It lists every tool the agent can reach for, built-in tools then Patch tools, each with what it does, its parameter definition, and an on/off switch. The OFF set is per chat, persisted on the device, and rides every turn the phone sends so the host drops those tools from the model's context. It is a page rather than a sheet because the list is long; the system back gesture returns to the chat. Its last row pads past the system navigation bar.

Chat title. The title is auto-generated; there is no rename UI. It is a human-readable name. `chatId` values (`chat_9f3a…`, `thread_…`) are internal and stay out of the UI (title bar, chat list row, notifications). A chat with no assigned name derives its title from content only: an auto-assigned name if present, else the first user message (truncated), else the durable first-message preview. When no content exists yet the title is "New chat" — it stays "New chat" rather than the folder basename, which would collide for two chats in one folder, or the raw id. Special threads use their fixed labels (Manager / Speakers).

Scroll position. The stream is a transcript, so opening a chat lands on the latest message (scrolled to the bottom of the `FlatList`), and while the user stays at the bottom new turns/streaming keep the newest message pinned in view. Scrolling up turns following off the instant the user starts, and the auto-scroll stops even mid-stream; scrolling back to the bottom re-enables it. What counts is the scroll the user makes, not where it lands: while a reply streams in the content grows under the finger, so the start of a deliberate drag up is still within touching distance of the end, and following judged on position alone re-pins the list out from under the gesture. Sending a message scrolls to the bottom and re-enables following, so the sent turn and its reply stay in view even if the user had scrolled up (matches `14-design-web.md` § Main chat panel). Only a scroll the user makes turns following off — a scroll the app makes itself, and any event the platform reports for one, never does. A send outranks the remembered position: a chat opened and typed into before its stream has settled stays at the sent turn rather than snapping back to where it was last left. Each chat's last scroll position is remembered per chat — reopening a chat the user had scrolled up in restores that position rather than jumping to the bottom. A chat opened at a message — from a search result — outranks both: that message is centred and briefly highlighted, and following is off. It is waited for while the transcript loads; if it never arrives (it is on another track), the chat opens as it otherwise would.

Messages — one-sided bubbles. Only the user's turns are a bubble: desktop's accent tint with a soft accent edge and normal ink, rounded with a flatter corner on the sender's side, right-aligned, capped to 85% of the width. The assistant's (and any system) reply is not a bubble — it renders as clean text on the page background, flush-left and using the full width of the stream (no fill, no border, no rounded card, no role label), exactly as a chat app reads on a phone. A phone is narrow and the agent's answers are the long side of the conversation, so boxing them in a raised card wastes a seventh of every line and makes a long answer read as a cramped card instead of a page. Markdown rendering, the voice mic glyph, inline attachments and delivery status lines are unaffected, and the ink stays the normal reading ink. This matches the web/desktop transcript (`14-design-web.md` § Main chat panel), where the assistant already flows flush-left with no bubble. The typing indicator keeps its small assistant-aligned dots card — it is a status chip, not prose.

The stream renders every event the agent emits — messages, tool calls, tool results, permission prompts. A permission prompt follows the same identity and answered-card rules as web (`14-design-web.md` § Main chat panel): one request id draws one card, a request already held is ignored when a replay re-sends it, and an answered request loses its options and reads its outcome. An `AskUserQuestion` permission prompt is not an approval and does not get the Approve/Deny treatment below — it follows web's Question-prompts rule instead (`14-design-web.md` § Main chat panel — Question prompts): the card renders the question and its options, answers travel back on `approve_with_edits`, and the call's own tool-call/tool-result rows are suppressed once the card covers them. Message text renders as Markdown (headings, bold/italic, inline + fenced code, lists, links) using the same renderer as web (`14-design-web.md`), not raw asterisks/backticks. A voice-origin user turn (the host tags spoken turns `[voice • <surface>]` — see `06-threads-manager-speakers.md`) shows a small mic glyph beside the bubble rather than the literal `[voice …]` tag text; the bracket tag is stripped from the displayed transcript.

A permission-mode change part-way through the conversation draws the same hairline rule with the mode named on it that web draws (`14-design-web.md` § Main chat panel), not a message.

Copying message text. Long-pressing any transcript row — a user bubble, the assistant's reply, a tool call, a tool result, a background-task row — opens a small bottom sheet with actions. Copy text puts the whole row's text on the clipboard (a message's markdown source; a tool call's summary, arguments and result) and confirms with a brief `Copied` toast; a copy that fails is an error toast. Select text opens a full-screen view of that row as one block of selectable text, where the OS selection handles pick out any part of it, with a Copy all action in its top bar. Text in the transcript itself is not natively selectable: a selectable leaf takes the long-press for itself, and the rendered markdown is many separate text runs a selection cannot cross, so a partial selection lives in the select view. A row with no text (an attachment-only message) has no long-press action. Pasting into the composer is the input's own native long-press → Paste: text goes in as plain text, an image is attached (§ Composer — Attachments). On a settled message row ONLY (user or assistant — not a tool call/result/background-task row, and not one still carrying a localId, which has no persisted fork point yet), the sheet carries one more action, Open side thread (§ Side threads screen, below).

On a message row specifically (one with a real persisted time), the long-press ALSO toasts that real clock time the instant the press registers — alongside the sheet opening, not a separate item inside it. This is the closest a no-hover surface gets to web's hover meta strip (`14-design-web.md` § Messages): the long-press itself is the reveal, so the time costs exactly the one gesture that opened the sheet, never a second tap to go find it.

A message with one or more side threads forked from it carries a marker beneath it — "Side thread" plus `· running` / `· needs you` while that branch is active (§ Side threads screen). Tapping it opens the screen on that tab.

The read-only mirror thread (Speakers) has no composer — in place of it a one-line hint says to reply from the source channel. Because there is nothing to type, an empty mirror thread shows a read-only empty state ("Nothing here yet", no "Type below…" line), not the standard composer-inviting empty chat state. Permission prompts other than `AskUserQuestion` (§ Chat detail, above) use the backend's exact options (for Claude Code: `1. Yes` / `2. Yes, allow all <X> during this session` / `3. No, and tell Claude what to do differently (esc)`). Big touch targets, no truncation of the option text.

Status bars. Above the transcript, below the top bar, the chat stacks the same bars web's chat panel does (`14-design-web.md` § Main chat panel), in web's order: the connection banners (reconnecting / host offline), then Goal, Tasks, Reminder, Provider-level context, Wake, Background tasks, Artifact bar, Archived, Hidden, Snoozed, and the host's sign-in state. Every bar gates itself — no bar when it has nothing to say — so an ordinary chat has none. They are compact: each is a single line at rest and only grows when tapped open, so several stacked still leave the screen to the transcript. Same data and the same REST routes as web; every edit is optimistic and reverts with an error toast if the host refuses it.

- Goal (`04-chats-and-folders.md` § Goals; matches `14-design-web.md` § Goal bar): one truncated line with a `◎` glyph — condition, running time, turns evaluated, tokens spent, and the evaluator's latest reason once one has landed (`Not met: …`), collapsed to fit on the one line and ordered by what fits first (condition always wins the truncation). The chevron (or tapping the line) opens the full bar — full condition, full reason, Edit and ×. Edit is tap-to-edit on the same text; saving re-arms the evaluator on the new text as a fresh goal (fresh counters). × clears it outright, no verdict recorded. Once resolved, replaced by a small `◎` in the chat header naming the outcome (`Goal met`/`Goal impossible`), tap for condition/duration/turns/tokens/reason — same data as web's finished-goal indicator.
- Tasks (`02-daemon.md` § Task list): collapsed, the item in progress (else the next pending one, else `All tasks done`) and `done/total`. Tapped open, the whole list is editable, because it is what the agent works from next: each item's status dot cycles pending → in progress → done, its text is tap-to-edit on the goal's rules, × deletes it, and a trailing `Add task` field appends one. Done items read struck through. Every edit sends the whole list.
- Reminder (`/remind`): one truncated line with a bell glyph; tapping shows the whole reminder; × clears it.
- Provider-level context (`02-daemon.md` § Provider-level context): one quiet row per category on web's rules (`14-design-web.md` § Main chat panel) — the category's label, `×N` once it has recurred, tapping open to its latest text. Its default expand state is the account's Provider-level context preference (§ Settings tab); `off` draws nothing.
- Archived: an archived chat names its state with Unarchive beside it — the very toggle the row tools and the ⋯ menu call. Archive is sticky; the chat still opens with its composer.
- Hidden: a hidden chat names its state with Show beside it — the very action the Hidden row's tray and the ⋯ menu call. No bar on an archived chat that keeps the flag.
- Sign-in: when THIS chat's host reports a definite `connected: false` for the chat's backend, a red-bordered bar reads `<machine> isn't signed in to Claude. Chats can't run.` (OpenAI for an OpenAI model) with Sign in, which opens Settings. Another host being signed out says nothing here, and nothing shows before the host has reported.

Wake bar (`02-daemon.md` § Self-wake; matches `14-design-web.md` § Main chat panel). When the chat has a pending self-wake, a bar sits above the transcript (below the top bar, alongside the offline/daemon-offline banners) reading how long until the wake fires and the wake message — e.g. `Wakes in 9m · check whether the bus has left`. The countdown is live (re-rendered every second) and switches to a bare `Wakes now` once `fireAt` has passed but the turn hasn't landed yet. No bar when nothing is armed, and it disappears the moment the wake fires or is cancelled. It is read-only — the agent owns its own timer; there is no way to dismiss it from here. This is the surface where a wake is most likely to otherwise go unnoticed: the phone is not left open on the chat the way a desktop tab can be, so the bar is what gives confidence a scheduled wake was not forgotten between opens.

Snoozed banner (`04-chats-and-folders.md` § Snooze). A snoozed chat still opens normally — from its Snoozed row, a deep link or a push tap — so instead of hiding anything the chat names its state: a bar beside the wake bar reading the wake time, carrying Unsnooze. Taking it returns the chat to the active list there and then. No banner when the chat is not snoozed.

Artifact bar (`14-design-web.md` § Artifacts — Artifact bar). When the chat has published one or more artifacts, a bar sits below the background-task bar, above the transcript: one chip per artifact, newest first, each reading the artifact's title. Tapping a chip opens that artifact exactly as tapping its transcript card would (§ Chat detail — Artifacts, below). It exists for the same reason as web's: the transcript already holds one card per artifact, but an earlier one means scrolling back to find it, so the bar is the standing index. Republishing the same file (same `artifactId`) updates its existing chip in place rather than adding a second one. No bar when the chat has published nothing.

Pending-response indicator. After the user sends and while the agent is composing a reply (the chat is `working` with no new assistant event yet), the stream shows an explicit in-thread loading indicator — an assistant-aligned bubble containing three animated dots (a typing indicator) rather than a spinner-plus-`Working…` label, so the user can see the send worked. All three dots share one beat, pulsing together rather than travelling in sequence, and the pulse is opacity alone — three dots hopping on the same beat reads as the row itself jumping (matches `14-design-web.md`'s "Thinking…" indicator). It clears as soon as the turn's first assistant-side event lands (an assistant message, tool call, or tool result after the user's most recent message); it does not wait on the row's `activity` flag, which can lag behind the last event and would otherwise leave the indicator stuck on screen after the reply has already rendered.

A background task completion arriving as a user turn still carrying its raw `<task-notification>` block (`02-daemon.md` § Background task completions) renders on the same rules as web (`14-design-web.md` § Background task completions): never a user bubble, but one quiet collapsed row reading the block's summary sentence — or `Background task` where it has none — that taps open to show the raw block.

A turn that carried captured `<system-reminder>` blocks (`02-daemon.md` § System-reminder disclosure) draws them on web's rules (`14-design-web.md` § Main chat panel): one quiet collapsed row per block under that turn's own bubble, reading the block's label, tapping open to the raw block. Collapsed always by default.

Tool calls are collapsed by default with a one-line summary; tap to expand args + result. The summary says what the call is doing and a consecutive run of more than one call collapses to a single row, on the same rules as web (`14-design-web.md` ## Main chat panel). Diffs render inline using a mobile-friendly unified format (no side-by-side; the screen isn't wide enough). A `patch_notify` call carrying `deepLink` shows a tappable link row on the collapsed summary itself (opens the link the same way a push tap does — `09-notifications.md` § `### push`) rather than requiring expansion first.

A `patch_delegate` call is a collapsible row, collapsed by default, carrying a live state pill, on web's rules (`14-design-web.md` § Main chat panel — Delegate tool row). Tapping the row expands the transcript inline beneath it, inside the parent chat — no screen of its own, no composer, no tool calls and no permission cards, just the subagent's own message exchange from `GET /api/chats/:parentChatId/delegates/:id/history`. A question the subagent asks mid-task never appears in it: it is mirrored onto THIS chat as an ordinary permission card (`02-daemon.md` § Native subagent dispatch), answered the same way any other permission prompt on this screen is.

Running delegates strip: on web's rules (`14-design-web.md` § Main chat panel — Running delegates strip), a line per running subagent (label + running time) sits directly above the composer; tapping a line expands the read-only transcript beneath it. Absent when none are running.

Artifacts (`14-design-web.md` § Artifacts). A published artifact appears in the transcript as its own card — the artifact's title and its source filename, nothing else — on the same identity rule as web: republishing the same file (same `artifactId`) updates the existing card in place rather than adding a second one. Tapping it opens the artifact full-screen in an in-app view — a sandboxed WebView loading the artifact's served URL — with a close control and an Open in browser action that hands the same URL to the OS browser (`Linking.openURL`). Mobile has no web panel to dock an artifact into, so this in-app view is the one place an artifact opens; Open in browser is there for anyone who wants it in their own browser/history instead. Every artifact the chat has ever published also stays one tap away from the artifact bar above the transcript (above), so an earlier one does not require scrolling back to find its card.

### Composer

Multiline text input at the bottom, laid out on two stacked rows. The input owns the full width of the top row so there is as much room as possible to read what is being written. The action buttons sit on a second row beneath it, in this order: `[camera][image][file][mic] … [model pill][padlock][Send | Stop]` — the attach and mic controls grouped at the left (see Attachments below), a flexible spacer, then the model pill, the permission-mode padlock and the send arrow at the right edge. The whole row fits a 360dp-wide phone: every icon button shares one 36px touch target, and the model pill is the one control that shrinks (it ellipsises), so Send/Stop is never pushed off the edge — even with the dictation clear control showing. Send/Stop paint a smaller filled circle inside that same target than the outline-only icons beside them, so the solid colour doesn't read heavier than its neighbours. There is no dedicated paste button crowding the row. Every control on the action row is vertically centred against its neighbours (icon buttons share one size token and one `alignItems:'center'` row — the mic must not sit high/low relative to the send arrow or the attach button). The input grows with what is typed and caps exactly as on web (`14-design-web.md` ## Main chat panel — Composer): the space it takes comes out of the stream above it, so the input's bottom edge and the action row beneath never move, and past the cap it scrolls internally instead of taking the screen. The cap is a fixed height rather than a share of the window, because the window Android reports changes as the soft keyboard opens and a derived cap would resize the field under the user's hands.

Model pill. Reads the model the chat's next message runs on as a compact friendly name (`Opus 5.5` — the catalogue label without the shared `Claude` prefix, or the id reduced the same way when the catalogue has not been read). Tapping it opens the chat's host's live model list (the same `ModelPicker` as § Model picker), fetched the first time it is opened rather than on every chat open. Choosing a model sends the same `chat.model_request` web's header crumb sends (`14-design-web.md` § Model selector): it applies to the next message — the list says so, adding that a running turn keeps its model — and the pill reads the pick, dimmed, until the host's `chat.state` confirms it. A host that has not confirmed within 8 s is reported and the pill goes back to the model the chat is actually on. No pill while the host reports no model. Beside it, in muted text, the label of the account the chat's latest turn ran on (`chat.state` `account`, `10-auth.md` § Backend credentials); not a control.

Permission mode padlock. The chat's permission mode for the next turn is a single icon button on the action row (there is no full-width "Permission mode" bar above the composer). The icon says which mode is in force: `default` a closed lock (neutral), `acceptEdits` a file-with-pen, `plan` a clipboard list, `auto` sparkles, and `bypassPermissions` an open lock in the danger red. Tapping it opens the mode list, opening over the composer, with friendly names — Ask before acting (`default`), Auto-accept edits (`acceptEdits`), Plan only (`plan`), Auto (`auto`), Bypass — no checks (`bypassPermissions`, in red) — the mode in force ticked. The value sent on `chat.settings` is still the SDK's own mode id (`02-daemon.md` § Permission mode); only the words on screen are friendlier. A mode the chat's model cannot run is listed greyed and cannot be chosen, on the same rule web's composer applies (`permissionModesFor` — `auto` needs a model that supports it). There is no option that clears the mode back to the host default; a chat always has a mode of its own. The model pill and the padlock are always on the action row of an existing chat — before the roster or the host has reported a model or mode they read empty (never a guessed value); only the new-chat screen omits them, its setup rows above owning the choice. With the link down the padlock is disabled rather than silently dropping a change.

Stop. While a turn is running and the composer is empty, Stop (a filled square) replaces Send in the same place and sends the same `chat.stop_request` web's stop button sends: the host interrupts the turn and settles the chat, and anything queued then drains. As soon as there is text (whitespace does not count) or an attachment, Send is back, and sending then queues the message behind the running turn exactly as a web send mid-turn is queued (`04-chats-and-folders.md` ## Message queueing). When the turn finishes, Stop goes back to Send. Sending a plain text message clears the composer before the host has confirmed the turn as running, so there is nothing left to send and nothing running yet to Stop; Send keeps its active colour and spinner across that gap rather than reading as dead for the moment before Stop can take over. A send with an attachment does not need this — its message already shows `Uploading` progress in the stream (§ Attachments).

Queued messages. A message sent mid-turn is drawn exactly as web draws it (`04-chats-and-folders.md` ## Message queueing, which owns the behaviour; same wire events): a right-aligned bubble in the block below the working indicator — the last thing in the stream — with a chip under it reading `Queued` or `2nd in queue`, `3rd in queue`… (position counted over the queued block, so removing or promoting renumbers at once), an always-visible ↑ that sends `chat.promote_request` (stops the running turn so the queue drains now; never reorders it) and an × that sends `chat.unqueue_request` and drops the bubble immediately. Tapping the bubble swaps its text for an inline editor with Cancel and Save; Save sends `chat.edit_queued_request` (an emptied edit with no attachments is a remove). If the message starts running or is removed while its editor is open, the editor closes, an error says so, and the edited text is appended to the composer draft. The chip is not the offline `Queued — will send when the agent reconnects` line (§ Offline), which waits on the host rather than a running turn.

Message hooks (`20-hooks.md`), full parity with web (`14-design-web.md` § Main chat panel — Message hooks): sending calls `POST /api/hooks/check` first; Send becomes **Checking…** (disabled, spinner) while it's in flight. `pass` sends as normal. `advise` sends and attaches a small expandable note naming the hook, for this surface's own session only (spec/20-hooks.md § Never reaches the agent — not part of the persisted transcript). `block` keeps the text in the composer and opens a sheet above it with the hook's name, analysis and suggestion (when given) and the same three actions as web: Use suggestion, Edit, Send anyway (which skips only that hook for this one send). A failed/timed-out hook renders its error in place of an analysis and offers Send / Edit only.

Agent-response hooks (`20-hooks.md` § On the agent's response), full parity with web (`14-design-web.md` § Main chat panel — Agent-response hooks): quiet by design, nothing on the composer. `pass` shows nothing. A `block` resubmit is an ordinary `hookTrigger`-tagged user turn, rendered as the same collapsed furniture a job trigger turn gets (§ Tool calls — Main chat panel, which mobile's tool-call rendering follows), summary naming the blocking hook; tap to expand the exact analysis/suggestion text, which is the turn's own content. An `advise` outcome, or a hook that failed/timed out, creates no turn: the note rides as a `systemContext` disclosure under whichever turn lands next, same tap-to-expand treatment, labelled "Hook advice" or "Hook failed". None of this carries a badge or a push — a `block` resubmit runs `origin: machine`, the same signal that already keeps a self-wake or todo auto-advance silent.

Goal verdicts (`04-chats-and-folders.md` § Goals), full parity with web (`14-design-web.md` § Main chat panel — Goal verdicts): a `not_met` resubmit is a `goalTrigger`-tagged turn, same collapsed-furniture treatment as a hook's `block`, summary `Goal not met — <reason>`. `met`/`impossible` create no turn — a system-role row marks the outcome instead, same tap-to-expand treatment; `met` rides the ordinary completion push, `impossible` raises the chat as needing attention like the hook loop guard does. The chat-list row carries the same small `◎` beside its badge that web's sidebar does (`14-design-web.md` § Sidebar), reading `chat.state.goal !== null` — informational only, no effect on sort or filter.

Unsent composer text belongs to the chat it was typed in, exactly as on web (`14-design-web.md` § Composer): the SERVER owns the draft, so it is restored when that chat is re-opened on ANY surface — not only the one it was typed on — live updates from another surface reaching this one the same way, deferred while this composer has focus and applied on blur or reopen. It never appears in another chat, and is cleared by a successful send, by deleting the chat, or by emptying the composer — typed then deleted leaves nothing to restore, and whitespace-only text counts as empty. Offline, the phone keeps what was typed on-device and pushes it once reconnected; a save that fails outright is reported rather than lost quietly.

The soft keyboard must not obscure the last message. When the composer keyboard opens, the composer stays above it (`KeyboardAvoidingView`; the Android window is `adjustResize`) and the stream scrolls so the last message stays visible above the keyboard — a `keyboardDidShow`-triggered scroll-to-end re-pins the newest turn after the list shrinks. This only re-pins while the user is following the bottom. Someone who has scrolled up to read history keeps what they were looking at: whatever sits at the top of the stream stays put as the keyboard opens, and the height the keyboard takes comes off the bottom of the view — the same as web (`14-design-web.md` § Main chat panel). The same holds when the keyboard closes and whenever the composer's height changes.

The composer mic dictates into the input for the chat you have open (`07-voice-app.md` § Dictation into the composer) — tap to start a toggle recording, tap again to end it, press-and-hold for hold-to-talk. Starting one puts the soft keyboard away and shows the listening strip above the input; the live words show in the input in full ink on the accent tint. A clear control appears beside the mic while a dictation is in flight and discards it without transcribing. The words land in the input to edit and send; nothing is sent by the mic itself. Starting a sustained voice call is a separate control — the phone icon in the chat-detail top bar (see § Chat detail) — so the two gestures are distinct and a tap dictates rather than calls.

Skill autocomplete. Typing `/` opens a list of the skills in the chat's folder on its host (`GET /api/skills?daemonId=&folder=`), filtered as you type (`/pl` → `plant`), anywhere in the draft it begins a word — the start of the draft, or right after whitespace or a newline — not only when the draft holds nothing else. The menu is active only while the token at the cursor is still open (no closing space yet). Tap a row to complete it (splicing `/<skill> ` in at that token, with a trailing space, leaving the rest of the draft untouched, which closes the list). A fetch error surfaces as an error rather than an empty list. The list defaults to the last-used skill for that folder — completing a skill remembers it (persisted on-device), and the next `/` sorts it to the top of the list (ordering only; the fetched set and the typed filter are unchanged). Otherwise the same behaviour as web (`14-design-web.md` § Skill autocomplete) minus the keyboard navigation, which is pointer/tap-driven here instead — rows are plain, though: a row's second muted description line and the list's own preview panel beside/above it are a web-only affordance for now.

Skill chips. Once a `/<skill>` token is complete — closed by the menu (which always appends the trailing space) or by typing the exact name and then a space by hand — it renders as a small tappable box in the draft instead of plain characters, wherever in the message it falls. Tapping a chip opens a bottom sheet with the same preview web's hover shows: full description, the rest of the frontmatter, an Edit link (addressed through the host files API — `daemonId` + absolute path, spec/03 § Host files — since mobile has no chat-scoped file browser); a skill with no description or no frontmatter shows only what it has. Backspace with the cursor right after a chip removes the whole `/<skill> ` in one press rather than eating it one character at a time; anywhere else Backspace behaves as it always has. Copy and paste carry the chip as its underlying `/<skill>` text, since a chip is compose-time rendering only, never a distinct stored value — pasted text with a `/<skill> ` in it becomes a chip the same way one that was typed does. What is sent to the agent is the literal text, unchanged, chip or not, in the same position it was typed — a chip never rewrites the message. That matters because only a `/` at the very start of the WHOLE message is a command invocation Claude Code itself recognises and acts on; a `/<skill>` chip elsewhere in the message is still just text to it, read (or not) exactly as any other word would be. The draft (§ Composer, above) stores this same plain text, so a chip already in a draft renders as one immediately on reopening the chat, without needing `/` typed again.

Attachments (images + files). The composer supports adding images and files without friction on both surfaces, but the attach controls differ by surface:

- Mobile keeps THREE clear attach buttons, side by side: a camera (camera icon → the OS camera, take a photo right now) AND a photo/image picker (image icon → the image library) AND a file picker (paperclip → the OS document picker, any file type) — these are genuinely different sources on a phone, and a phone is the one surface where the thing you want to send often doesn't exist yet. The camera is one tap, not a hidden long-press: it requests the camera permission (denied → a loud error), opens the camera, and a captured photo becomes a normal image chip that goes through the same downscale-then-upload path as a picked image. A cancelled capture adds nothing. The camera button is mobile-only — web/desktop has the screenshot-grab button instead. Both mobile pickers open in MULTI-SELECT mode (the camera is inherently one shot per capture) (`allowsMultipleSelection` / `multiple: true`) and the file picker asks for any type explicitly (`type: '*/*'`, `copyToCacheDirectory: true` so a cloud-provider pick lands as a readable local file) — one trip through the OS picker brings back every file the user chose in one go. Each picked asset becomes its own chip and its own upload on send. Web/desktop collapses these into a SINGLE attach button (paperclip): one OS file dialog accepting images and any file (the separate image button opened the identical dialog, so it's removed). Web/desktop also adds a screenshot-grab button (screen-capture via `getDisplayMedia`, one frame → PNG) — not on mobile. Attaching covers any file on both surfaces.
- Paste — pasting an image from the clipboard (screenshot, copied image) attaches it directly. On desktop/web it is `⌘V`/`Ctrl V` into the composer. On mobile it is the input's own long-press → Paste, as in any other Android app: with an image on the clipboard, Paste attaches it instead of inserting text. An image a keyboard inserts — a Gboard GIF, sticker or clipboard-suggestion image — attaches the same way. Either becomes an ordinary image chip (same downscale and upload as a picked image; a GIF or sticker within the size cap is sent as it is). A clip holding both text and an image pastes the text into the input and attaches the image. There is no paste button or chip. Text paste of 10,000 characters or more (one change that grows the input by that much) is taken out of the input and attached as a document named `Pasted – <first six words>.md`; a failed write is an error toast. Text paste is unchanged — plain text, into the input. An image that cannot be read is an error toast naming it; the rest of the paste still lands. Android only offers an image to an input that declares it takes images, which React Native's input cannot, so this rides on a native listener on the composer input (the `PatchPaste` module, APK 0.1.3+).
- Images are resized/compressed before sending. Client-side, the longest edge is capped at ~1568px and the image re-encoded to JPEG (~0.85 quality) so it's within the backend's vision limits ("image was too large to process"). Mobile uses `expo-image-manipulator`; web uses a canvas resize. Non-image files upload as-is.
- What the agent reads is not what the user sees. Where a resize happened, web/desktop uploads BOTH blobs under one attachment id: the original and the resized copy. The server stores and serves back the original, so the stream and the lightbox show the image at full size, while the resized copy is the one handed to the host for the agent to read. An image already within the cap has no second blob — the single upload serves both purposes, as it does for non-image files. Mobile uploads the resized copy alone, so an image sent from the phone renders at the resized size.
- Attachments show as removable thumbnails/chips above the input before sending; they upload with the message and render inline in the stream. Sending with attachments reacts at once, exactly as a text send does: the composer clears and the message appears in the stream straight away, its attachments drawn from the local copies, in the pending style with an `Uploading` status that counts the uploads that have landed (`Uploading 1/3`). Only once every attachment has uploaded is the turn sent, and from there it is an ordinary send (`12-error-and-offline.md` § Guaranteed input delivery); the agent never receives a message with some of its attachments missing. A failed upload leaves the message in the stream marked `Not uploaded`, surfaces the error, and offers Retry, which uploads the same files again, and × to discard the message. The composer stays usable while a message uploads, and a message sent behind one still uploading in the same chat appears at once too but is sent only after it, so turns reach the agent in the order they were sent; a failed upload does not hold up the messages behind it.
- A first message WITH an attachment always has a real chat to upload to. The upload endpoint needs a real chatId, so on both surfaces a new chat's first send creates the chat before uploading (§ New chat flow; `14-design-web.md` § Attachments). Neither surface uploads to the literal `new` placeholder.
- Tapping an inline image opens an in-app zoomable viewer rather than an external link or browser tab: a full-screen overlay with pinch-to-zoom + pan (mobile: a `Modal` with a `PanResponder`-driven zoomable `Image`; web: a lightbox overlay with click/scroll-to-zoom and drag-to-pan, Esc/backdrop to close). Non-image files still open their served copy.
- Attachments persist on replay. Leaving and returning to a chat re-renders the image/file rather than a literal `[attachments]` marker. The backend's transcript only carries the turn's text (with the host's appended `[Attachments]` path block), so the host persists each attachment ref in a per-chat manifest at upload time and, on history/replay (`chat.message`), reconstructs the structured refs and strips the path block from the displayed text. The client renders the reconstructed refs inline.

A voice note draws its overlay over the bottom of the screen; a call docks its bar above the composer (§ Voice states). Both persist if the user navigates to another app — Android's foreground service keeps audio alive, and they re-attach when the app is foregrounded again.

## Side threads screen

`04-chats-and-folders.md` § Side threads / § Parallel branches; `14-design-web.md` § Side threads panel for the desktop/web equivalent. Mobile "stays the single view it has always been" (`04-chats-and-folders.md` § Branching) — no docked panel — so a side thread opens as its OWN pushed screen, same shape as the Tools page (§ Chat detail; reached via the chat's ⋯ menu → Tools): a top bar with Back to the main chat, a tab strip across the top, and one tab active at a time.

- Trigger: the long-press sheet's Open side thread action (§ Chat detail, above) on a settled message, or tapping a message's own side-thread marker. Either pushes the screen.
- Tab strip: one tab per side-thread branch (`chat.branches`, `sideThread: true`), each a status dot (needs-you over running over idle, same priority as web) and the branch's name/label. No close control on mobile — the strip is a horizontal scroll, not a fixed-width row competing for space the way the panel's desktop tab bar does.
- The trigger's draft: a tab opened by the trigger is NOT a branch yet (the host mints the id) — it shows the quoted "Off <message>" line and an empty, focused composer. Sending fires `chat.side_request`; the draft is replaced by the real tab the moment `chat.branches` reports the new branch (pull-based, same substitution web's panel makes — nothing is pushed for a branch that isn't broadcasting live).
- Each real tab is a small chat of its own: the quote line, that branch's own transcript (`GET /api/chats/:id/history?branchId=`, polled while `running`, fetched once otherwise), its own composer (`chat.input {branchId}`), Stop while running (`chat.stop_request {branchId}`), and that branch's own permission cards (a branch-tagged `chat.permission_request` renders here, never in the main chat's transcript, which draws only the active branch).
- Branching again from inside the screen: the same long-press on a message inside a tab's own transcript opens a draft parented to THAT tab's branch (`chat.side_request {branchId: <this tab's branch>}`), landing as another tab.
- Send back to chat: `chat.send_back_request {chatId, branchId}` on every real tab, disabled once the branch's `sentBack` flag is set.

## Voice states (visual)

- Mic button idle: grey.
- Voice-note overlay (single-turn): dark capsule pinned above the bottom edge, in three named states. While recording: a pulsing mic and `Recording… 0:05`, the timer counting up — a note is uploaded whole, so there are no words to show while the user talks (`07-voice-app.md` § End-to-end voice transport) and the timer is what says the mic is alive. While uploading: `Transcribing…`, send and cancel disabled. Once transcribed: the whole transcript, scrollable and never clipped to a line or two, with a close control; it clears itself after a pause long enough to read it (scaled to its length, 4–15 s), and scrolling it hands it to the close control instead. A note that transcribes to nothing says so and closes. There is no instructional caption. Both gestures are supported and a `hold`/`tap` mode governs how the note sends:
  - Hold-to-talk (press-and-hold): releasing (the `onPressOut` on the mic caller) sends. Release-to-send applies only in this mode.
  - Tap-toggle (tapped to start): a second tap, or the overlay Send control, sends; a finger-release does not send.
  - The recording overlay leaves the soft keyboard down — it is a voice surface; the composer text input is blurred and made non-editable (so it cannot refocus) while recording, and the keyboard is dismissed.
- Voice call (persistent): not a full-screen layer. The call lives inside its chat: the chat's message stream is the transcript — each spoken turn and each reply lands there as an ordinary message — and a call bar docks above the composer, which stays usable. The bar carries, top to bottom:
  - A status line: a dot, what the line is doing, and the elapsed time counted from when the session connected. `Connecting…` with counting dots and a neutral dot, and no timer, until the host acknowledges the session; then `Listening` (dot pulsing), `Hearing you`, `Thinking`, `Speaking`, or `Muted`.
  - The words in flight, prefixed `You:`, in full reading ink while the user speaks. In `hands-free`, an utterance that was not addressed reads `Heard "…" — not addressed, so not sent`, greyed.
  - In `hands-free` only, a one-line hint of what makes it respond: `Start with "<address word>" — or reply within 30s of it speaking`, naming the account's address word.
  - Controls: Mute, a two-segment switch naming the modes plainly — `Call` (every utterance is a turn) and `Hands-free` — with the one in force filled, and End.
  - A failed session (`07-voice-app.md` § 2. Voice call) replaces the status with `Could not connect` or `Call problem`, shows the reason and a Retry that reopens the same chat in the same mode; End still ends it. A hosted engine's failure names the engine (`Gemini Live failed — …`, `OpenAI Realtime failed — …`); a refused voice-config cell reads `Not available with this voice setting — …`.
  - On a hosted backend (`07-voice-app.md` § Voice is a config matrix), the engine and its effective layer in small quiet text beside the timer (`Gemini Live · heavy`, `OpenAI Realtime · light`). Nothing on `local`.
  - The mode switch reopens the session on the same chat when the two modes are configured onto different engines, and flips it in place otherwise.

  The call is two-way and live: the user's speech is streamed to the host, transcribed and answered, and the agent's TTS reply is played back through the speaker (a native `AudioTrack` sink) so the user hears it — a call where "nothing happens when I speak" or where the reply is silent is a failure the surface reports (see `07-voice-app.md`).

- On-call pill: while a call is open and the user is anywhere other than its chat, a small pill stands in for the bar — `On call · Manager · 1:23` (`Hands-free · …`, `Connecting… · …`, `Call failed · …` as the state requires). It floats just above the tab bar on the tab screens and docks above the composer of any other chat. Tapping it returns to the call's chat; its red button ends the call.
- Manager incoming call (system-level): see Manager incoming-call UX below.

See `07-voice-app.md` for mechanics.

## Voice tab (Manager)

Tapping the Voice tab opens the Manager thread directly. Inside: full chat-detail rendering (the Manager thread is just a chat) — the composer mic records a voice note to Manager, and the top-bar phone icon starts a Manager voice call.

The tab itself is a plain tab (icon + label), not raised — the raised button in the bar is New chat's — but its press behaviour still advertises "this is the way to talk to your assistant": one tap opens Manager, tap-and-hold the tab for a quick voice note. It's the mobile counterpart to the desktop menu-bar's global PTT chord.

A segmented control directly under the Manager top bar switches the screen between **Conversation** (the thread, the default on every open) and **Chats** — the phone's counterpart to the desktop Threads strip (`14-design-web.md` § Manager view). Chats lists every active chat on every host, needs-you first: a pending permission, then a declared question, then a report, then working, then the rest by recency — the one rule in `@patch/wire` (`threadRows`) that the desktop strip also calls, so the two never disagree. Archived, snoozed and deleted chats are not listed, nor are the special threads. Each row shows the status badge, the chat name, its host and folder, a word for the states the badge cannot tell apart (`needs approval`, `question for you`, `report`), and the one-line status summary. Its controls are the decision it is blocked on: Approve for a pending permission (the same `chat.permission_response` the chat's own card sends; an `AskUserQuestion` is not approvable here and has to be answered in the chat), Stop for a running turn; tapping the row opens the chat. A send that cannot go out because the link is down surfaces as an error toast, and the row stays as it was. With nothing active the tab shows the "Nothing running" empty state. The conversation stays mounted, just hidden, while Chats is showing, so its scroll position and composer draft are where they were on the way back.

A hands-free control sits beside the phone icon in the Manager top bar. It opens the same sustained session in `hands-free` (`07-voice-app.md` § Session modes) — the line left open for plastering a wall or a long drive.

The sweep's slim status line and its "Check now" control (`06-threads-manager-speakers.md` § The sweep; `14-design-web.md` § Manager view) are web-only for now — the account-wide setting still applies equally (Settings is one surface regardless of which device opens it), but the phone's Chats tab does not yet draw the line itself.

The reach switch (`09-notifications.md` § Reaching the user) sits at the top of the Voice tab, where it is reachable in one tap before setting off. It is the control for the case hands-free cannot serve: a podcast playing, with Patch reading its interrupts out over the top.

A session in either mode runs under a foreground service and survives the screen going off and the app going to background; a session Android drops while the phone is in a pocket is the failure that service prevents. Its ongoing notification names the mode and carries Mute, a mode switch and End call. Audio focus is `AUDIOFOCUS_GAIN` for the session's whole length — the session is what the device is doing. A spoken `auto-notify` interrupt, which holds no microphone, instead takes transient-exclusive focus for the length of the message so a podcast pauses and then resumes (`07-voice-app.md` § Speaking with no session open).

## Empty states

Every empty surface uses one pattern. A centred lucide icon (touch-sized, `ink-3`), an upright-Fraunces title, one line of `ink-3` helper text as a plain sentence, and the primary action button when one applies. Canonical cases:

- Empty chat — an on-brand illustration (the patch chat-bubble mark — three activity dots — with a small leaf sprout, in the leaf-green accent), NOT a bare lucide icon or plain placeholder text, above just the "No messages yet" title. It carries no helper line — the one empty state without one, matched on web (`14-design-web.md`). (Read-only mirror threads keep the plainer icon empty state, since "type below" doesn't apply.)
- Empty read-only mirror (Speakers, which has no composer) — a message icon + "Nothing here yet" + "Messages appear here as they arrive." — the "Type below…" line is omitted because there is nothing to type into.
- No chats — patch mark + "No chats yet" + "Tap + to start one."
- No jobs — a clock icon + "No jobs yet" + "Ask Manager to create one, or add one here."
- No channels — a channels icon + "No channels yet" + "Speakers appears here once connected."
- Nothing snoozed — a clock icon + "Nothing snoozed" + "Snoozed chats wait here until their wake time."
- No batch running (§ Batch view) — a layers icon + "Nothing batched" + "Press Batch to start one."
- Nothing needs attention (§ View dropdown) — an inbox icon + "Nothing needs attention" + "You're all caught up."
- Empty host folder (§ Host files and terminal) — a folder icon + "Empty folder" + "There is nothing in this folder."
- No devices, no secrets, empty chat search follow the same shape.

Helper text is always a plain sentence — no parentheses, no brackets.

## Settings tab

Settings on the phone is at parity with web's Settings page (`14-design-web.md` § `/settings` details): the same sections, under the same names, in the same six groups and the same order, reading and writing through the same REST calls and wire frames. Every section has the same shape — a sentence-case label in the body face over one raised card holding its controls — drawn by one shared component, so no section reads in a different face or size. A section is its header plus its controls — there is no descriptive subtitle line under any section header; the controls speak for themselves. Each section is its own component (`apps/mobile/src/components/settings/`); the screen only orders them.

Several sections read the one `GET /api/settings` payload web's page reads (Linked devices and every account-wide preference). It is fetched when the tab opens and refreshed every 15 seconds while it is open, as web polls it. Until it has answered, those sections show a loading affordance; if it fails they show the failure with a Retry — never a stand-in set of default values presented as the account's. Every write settles on the server's or the host's answer rather than being patched locally, and a failed write says so. Every host-scoped edit is addressed to that machine and is refused up front, naming the machine and when it was last seen, when either this phone has no link to the server or the machine is offline — the server would otherwise buffer the frame and apply it whenever the machine next connects.

1. Account & connection
   - Account — a This device value (name where known). Identity is shown instantly: this surface's identity is read from the locally-held credential (the surface JWT carries the surface id, kind and label) and painted on first render — there is no spinner and no network wait for values the device already knows. `/api/auth/me` runs only as a background refresh; it must not gate first paint. A value that is genuinely unavailable reads "Unavailable", never a dash. The account id (the long account public key) is NOT shown — it does not fit a value row and serves no user purpose on a phone.
   - Connection — the server this phone is connected to, and that server's git SHA (`GET /api/healthz`). A failed read is said, with a Retry.
   - Version & updates — what the phone is running (version and commit, build time, last check) and the one action that applies: Check for updates, Restart to update once an OTA has downloaded, or Download APK when a newer build cannot reach this phone by OTA (no update channel, or stuck on an old native runtime) and the phone reaches its server directly — see `11-deployment.md` § Mobile OTA. Below it, the same cross-layer report web shows (`GET /api/version`): any drift between layers first, each with its remedy, then per-layer detail (deployed UI, server, each host, the published APK, each connected client) behind a Details disclosure.
   - This surface — a single Deactivate surface action (the wording is Deactivate, never "Log out"/"Sign out"), confirmed before it runs, exactly as on web: it self-revokes on the server (`POST /api/auth/revoke` with this surface's id), clears the local credential and returns to pairing. Cancelling does nothing at all. A failed revoke still clears locally and says the revoke failed.
2. Agent behavior
   - Agent behavior — the same shared rows as web (`14-design-web.md` § Agent behavior): the layers patch adds on top of bare Claude Code, each with its stated default (CLAUDE.md, Patch tools prompt with Reset to default, Memory, System prompt override, Skills, Browser tools), default permission mode, Questions, Auto-resume, Chat names, and Claude Code settings. Saved to the server (`01-server.md` § Settings); text fields save when they lose focus.
   - Model — the account's default model for new chats, chosen from the home host's catalogue; a saved model the catalogue no longer lists stays selectable.
   - Chats — Warn before switching provider, and Provider-level context (Off / Summary / Full), the same account preferences web's Chats group writes.
   - Hooks — full parity with web's Hooks page (`14-design-web.md` § Hooks, `20-hooks.md`): the list (name, kind, enabled switch) and an editor opened by row or by Add, same fields, same Save/Delete.
3. Voice — the Kokoro voice, and the per-surface config matrix (Dictation, Voice device, Hands-free, Call; backend and, for the three conversational surfaces, front layer). Every combination is selectable; a cell that is refused, or that runs as something other than its name (a hosted `direct` runs as `light`; Gemini hands-free does not apply the address word), says so, in the same words web uses.
4. Credit sources — the shared accounts, as on web (`14-design-web.md` § Credit sources), with each backend's strategy as a row of chips above its accounts and Move up / Move down in each row's ⋯. Claude: one row per account in order (Connected with the email, or Not connected; Connect reveals a token field; Disconnect is confirmed; each names its own account id), its usage bars (5-hour, Weekly, Extra usage — a never-bought extra-usage add-on reads as off, not blocked) with when each resets, when it was read, and a Refresh, a warning when two rows share one Claude organisation, Add another Claude account (token required, optional label), and an Adopt control per host with a login of its own not already stored. A change is settled by the server's reply, and a token the server could not validate is refused with the reason. OpenAI accounts on the same terms (sign in with a code, find an existing Codex login on a host, or an API key). Keys — the provider keys, as on web.
5. Hosts & devices
   - Hosts — Add a host above the list (the server's install command, the platforms it has published builds for, and a single-use pairing code re-minted before it expires; nothing published says so and mints nothing). One row per host machine: its name (tap to rename; an empty name is refused), home marker, online/offline stated exactly once with the last heartbeat, platform and host version, Update when one is available, Make home, its agent backends with a Sign in control on any that needs one (a Claude token field; a Codex backend opens that host's OpenAI form in Credit sources), the settings version it is running with (or why it refused the latest), and how many of its chats carry a per-chat permission mode. Details expands the rest: Project folders (remove per row, add by path; "hasn't sent its folder list yet" until it has) and Claude Code (memory entries with remove, and a drifted `settings.json` with Keep as shared, Keep for this OS and Discard; absent until the host reports them). Each reported host's row also carries Files and Terminal (§ Host files and terminal), unpressable while that host is offline or the link is down. A machine that has not reported yet is shown as awaiting its first report. When a host is offline this is where the offline banner links to (see § Offline / error states).
   - Linked devices — the surfaces on the account (`/api/settings`), each with a human-friendly device name ("Phone", "Desktop", "Web", never a doubled token or a raw id as the primary label — the id may appear as secondary muted text), the current one marked This device, and a Revoke on each other (`POST /api/auth/revoke`). The registered Android-device count is a value in this section. Link a device mints a genuine single-use nonce (`POST /api/auth/pair/start`) only when opened and shows it as a QR — drawn dark-on-light in either scheme so it scans — plus the code as text; the new device scans it.
   - Voice devices — as on web: a voice device has no screen or camera, so no code or QR is offered; the section says how one is adopted.
   - Secrets — mobile only: a key-value store for tokens/credentials the host injects into chats (not the host's own provider keys, which are under Settings → Keys). Editable from any surface: add a key, set/replace its value (a write-only field; existing values are masked behind a Reveal toggle), and delete. A failed read is shown with a Retry rather than as an empty list.
6. Special threads
   - Sweep (`06-threads-manager-speakers.md` § The sweep) — Enabled, interval, stalled threshold, messages per chat, the sweep prompt (opens the same full-text editor pattern as web, with Reset to default) and the model it runs on.
   - Manager — quiet hours (24-hour `HH:MM` fields; anything else is refused and the field returns to the saved value), the context window (§ Manager conversation — bounded context) and the address word.
   - Goals (`14-design-web.md` § Goals) — the judge model (one for every chat, default Sonnet 5.5), how many refusals in a row end a goal's pushing (a positive whole number; anything else returns the field to the saved value) and the judge prompt, opened in the same full-screen editor as the other prompts with Reset to default.
   - Manager & Speakers — the model those threads run on (from the home host's catalogue, separate from the default model) and scheduled session rotation: a switch and the time of day.

Left out because they are desktop-only by nature: the desktop shell's own updater rows in Version & updates, and Run a host on this Mac. There is no Jobs section — Jobs is a bottom tab of its own (§ Navigation shell, § Jobs screen), not a row here — and no separate Host block with its own unlink: the machines are listed under Hosts, and leaving the account is Deactivate surface.

### Jobs screen

A bottom tab of its own (§ Navigation shell), not a page section — full parity with web's dedicated `/jobs` page (`14-design-web.md` § Jobs view), touch-native rather than a port of `<select>` controls:

- Header with the title and an always-present "New" action (independent of list state — not conditional on the list being empty or non-empty). No back control: it is a tab root, so there is nothing beneath it to go back to.
- The job list: one row per job, showing name, trigger summary (natural-language, as web renders it, including the zone it runs in when that is not the device's own), the action's verb + target, when it last fired (or "never"), an "N queued" tag when fires are backed up behind its concurrency limit, an open-chat link when the job has a chat to link to, and an inline enable `Switch` (toggling calls the enable/disable endpoints directly from the list, no need to open the editor for that). An empty state replaces the list when there are no jobs yet; the New action is still reachable above it.
- A search box sits between the header and the list, on the same rules as the Chats tab's local filter (§ Chats tab → Search): instant and local, filtering the already-loaded jobs on every keystroke with no request and nothing to submit. A job matches when the query appears, case-insensitively, in its name, its id, its trigger type, its cron expression, its trigger summary, or the action's verb and target. Matches keep the list's order. A query that matches nothing shows an empty state in place of the list. The box is only shown when there are jobs to search.
- Beside the search box, a Sort control and two Filter controls — each a pill naming its current choice, opening the same option-sheet picker the job editor's Folder/Model/Skill fields use. Sort orders the rows within every section by last fired (most recent first, never-fired last — the default), by name, or by when the job was created (newest first); it never changes which sections are drawn. The filters narrow on status (any / enabled / disabled) and on trigger type (any / cron / recurrence / webhook / todoist). All three compose with the search and with each other. Drawn under the same condition as search — only when there are jobs to narrow.
- The list is grouped into four sections, in this order: the recurring jobs, the one-off jobs still waiting to fire, the expired ones, then the archived ones. A section with nothing in it is not drawn; an installation with only recurring jobs shows the plain list it always did, no section header at all. Recurring and one-off are always open; Expired and Archived are each collapsed by default behind a header naming the section and its count, and stay open/closed for the rest of the session once tapped.
- An expired or archived row is muted and its enable `Switch` is disabled — neither job fires, so a live switch would lie about what it does. Each row also carries Archive and Delete actions: Archive is reversible (the same control reads Unarchive on an archived row and restores it to the section it came from) and asks nothing; Delete is permanent and asks for confirmation first, the same confirmation the editor's Delete asks for.
- A cron row's trigger summary names the zone it runs in when that is not the device's own, as web does (`14-design-web.md` § Jobs view).
- Tapping a row opens that job's full editor (§ Job editor); tapping New opens the same editor blank.

### Job editor

Tapping a job row opens a working editor with parity to the web one (`14-design-web.md` § Jobs view) — not a read-only summary:

- Name, an optional Group picker beside it (`08-triggers-and-jobs.md` § Groups — what the list's user-group headings would read; empty means ungrouped, always sent, never omitted), and the enable toggle. Group is the same dropdown-plus-"New group…" shape as web (`14-design-web.md` § Jobs view) — the mobile Folder/Model/Skill `OptionPicker` offering every distinct group already in use, with a trailing New group… option that reveals a free-text field for a name not yet used.
- Beside the title, a small "ONE-OFF" label for a job carrying `oneOff` and a second "EXPIRED" label once it has retired (`expiredAt` set) — read-only, parity with web's header chips (`14-design-web.md` § Jobs view). Neither field has an editable control on this page; both are shown so opening the job explains why its list Switch is disabled without going back to the list's own grouping.
- Trigger type select + its natural-language config.
- For a cron trigger, a single natural-language Schedule field ("every weekday at 9am", "every 15 minutes", "every 5 minutes between 9am and 5pm"); the computed cron expression + plain-English description show read-only beneath it, with an "edit cron directly" toggle for the raw 5-field expression (auto-revealed when a phrase can't be parsed).
- A Timezone field beneath Schedule names the zone the expression runs in (`08-triggers-and-jobs.md` § Cron), typed as an IANA name and shown alongside the computed cron. A new job defaults to the device's zone; an existing job shows its stored zone, or UTC when it carries none. A name the device can't resolve blocks the save and says so.
- Filter — shown only for payload-bearing triggers (webhook / todoist); hidden for cron.
- Action — the two axes: where (`spawn` a new chat / `ensure` one persistent chat / `message` an existing chat) and what (run a `skill` / run a `prompt`). `spawn`/`ensure` use the host folder picker (§ New chat flow); `message` uses a recipient-chat picker; `skill` is a dropdown of the target folder's skills. `spawn`/`ensure` also carry the Model choice, offering the chosen host's catalogue led by `Host default`, exactly as web does (`14-design-web.md` § Jobs view). A job is durable configuration rather than a chat being started now, so `Host default` is the leading option: no stored model means each fire takes whatever that host resolves at the time.
- `ensure` carries a Deduplication key field beneath the folder/model fields — a Mustache template evaluated against each fire's payload; fires that render the same key resume one chat instead of starting a new one, and an empty key means a single chat shared by every fire (`08-triggers-and-jobs.md` § Action).
- `spawn` carries a Permission mode picker, the same mode names and order the composer's own padlock offers (§ Composer). A new job starts on Auto, which is also what a job storing no mode shows; unlike Model there is no `Host default` choice — a job runs unattended, so it must name a mode of its own rather than following whatever its host is currently set to.
- Two toggles sit beneath the Skill/Prompt fields for `spawn` and `ensure` (the two actions that create a chat): Hide chat from sidebar, which puts every chat this job creates into Hidden rather than the ordinary inbox; and Notify when job complete, which starts ON and rings the completion doorbell for a chat this job created once it settles.
- A selected skill carries an Edit link beside the picker that opens the skill's own file in the host file editor (§ Host files and terminal), addressed by host + absolute path with no chat needed (`03-wire-protocol.md` § Host files) — the skills list already names the file each skill is defined in, so the link never guesses a path, and unlike web's chat-scoped file browser it reaches a skill anywhere on the host, including a machine-wide one under `~/.claude/skills`. Nothing is drawn until a skill is chosen; where the host hasn't reported skill files (an older host) or its target folder/host isn't known yet, the link is replaced by the reason it cannot be offered.
- Save persists via the job REST endpoints; a `spawn` or `ensure` action with no folder or no host is blocked with a clear message, matching the API's own rule (`08-triggers-and-jobs.md` § Action).
- Run now — shown only for an existing job (not the new-job form), beside Save/Delete: fires the action immediately, once, for trying it out without waiting for the real trigger or enabling the job first (`08-triggers-and-jobs.md` § Manual run). Mobile has no persistent runs panel, so outcome is a plain `Alert` (sent/queued/buffered, or the error) rather than a panel update.

## Host files and terminal

A host's files and a shell on it, with no chat in between — for running a command or editing a skill or config on that machine. Reached from the host's row in Settings → Hosts. Each screen acts on one host, named under its title.

Where it starts. Both screens start at the host user's Home or at one of that host's published project folders (`04-chats-and-folders.md` § Folders), roots then recents. Home's absolute path comes from the host (a listing with no path reports it); the phone never guesses it.

Files. One directory per screen, backed by the host files API (`03-wire-protocol.md` § Host files); opening a folder pushes the next screen, so back walks up the way the user came. A strip of place chips (Home, then the project folders) sits across the top, marking the place on screen. Under it: the directory's name with its absolute path muted beneath, Up a level (absent at `/`), then its entries — hidden ones included, folders first, files with their size. A dangling link is listed and cannot be opened. An empty directory shows the empty-state pattern (§ Empty states); a listing that fails shows its reason in place of the list. A terminal action in the header opens the Terminal in the directory on screen.

Editor. Tapping a file opens it in a full-screen plain-text editor: monospace, no autocorrect or auto-capitalisation. Nothing is written until Save is pressed; Save is disabled while nothing has changed, and a dot after the file name marks unsaved edits. A save goes over the version the file was opened at: if it changed on disk since (the agent edited it, another surface saved it), the host writes nothing and the editor says the file changed on disk, offering Reload (discarding the edits) or Keep editing. Any other failure is reported with its reason and the edits kept. Back — the header's or the system's — with unsaved edits asks before discarding them. A file the host will not open (binary, over 1 MiB, unreadable) shows the reason instead of an editor.

Terminal. With no folder given, the screen first lists where to start (Home, then the project folders). It then opens a PTY session (`02-daemon.md` § PTY sessions) sized to the emulator and draws it with a real terminal emulator — xterm.js in a WebView, bundled with the app so it needs nothing from the network — in the app's theme colours. The page draws what it is given and reports keystrokes, size changes and the terminal's cursor-key mode; everything else is decided on the React Native side. Tapping the terminal brings up the keyboard.

- A key bar above the keyboard supplies what a phone keyboard lacks: Esc, Tab, Ctrl, ↑ ↓ ← →, `|`, `~`, `/`. Ctrl is sticky — tap it, and the next key, from the bar or the keyboard, is sent as its control character; it shows armed until then, and tapping it again disarms it. Arrows follow the terminal's cursor-key mode (application mode inside full-screen programs); Ctrl on an arrow sends the modified-arrow sequence.
- Until the shell is live a status line says Starting…. A session that ends or fails says why (the shell exited with its status, closed, idle timeout, host restarted, the host cannot open a terminal, the link is down) and offers Restart, which opens a fresh shell on a cleared screen. A host whose host answers with a pipe shell instead of a PTY is refused with a message to update it, and that shell is closed.
- The phone keeps the session's scrollback, so a rebuilt emulator page (a theme change) is redrawn in full and the host told its size.
- Leaving the screen closes the shell on the host.

## New chat flow

Tapping New chat (the New chat bottom tab, § Navigation shell, or the New chat action on the Chats tab's empty state) opens the new-chat screen. It is type-first, the same shape as web's new chat (`14-design-web.md` § Sidebar §8): the composer is at the bottom from the start, and the chat's setup sits above it as rows of one-tap choices.

- Folder — one pill, reading `<folder name> · <host>` once chosen, else `Choose a folder…`. Tapping it opens the folder picker SHEET (§ Folder picker sheet below) — the same model the web/desktop popover follows (`14-design-web.md` § New-chat setup row → folder picker): one search box, no separate host row and no row of quick-folder chips. Picking a folder in it picks the host too; there is nothing else to choose host with. A folder on an offline host is refused with a message saying that host is offline; picking a folder on a different host than the screen was on clears the model and mode chosen on the previous one.
- Model — the three most recently used models on that host, counted over the chats the user started exactly as web counts them (`14-design-web.md` § Sidebar §8), topped up from the head of its catalogue; only models the catalogue offers appear, so an unloaded catalogue leaves only the model pill (§ Model picker), which opens the full list.
- Account — when the model's backend has more than one connected shared account, chips for `By strategy` (selected by default) and each account, naming the one the chat's turns start on (`10-auth.md` § Backend credentials — preferred account).
- Permissions — one button naming the mode the chat will start in (the shared default until one is picked), opening the same mode list as the composer padlock (§ Composer).

The screen opens on the host and folder it was handed (chat detail's ⋯ → New chat), else on what the last NEW chat created from this screen used (host, folder, model, permission mode — recorded only when a new chat is created here, never by a job, a hidden thread or a continuing chat; read once on open and the recents and model picks are fixed for as long as the screen shows, so nothing changing elsewhere moves them), else the home host with no folder chosen; with several hosts and no home host none is guessed. Untouched, the model and mode are not sent — the host resolves its own (`04-chats-and-folders.md` § Spawn).

Nothing exists on the server until the first send. Send creates the chat (`POST /api/chats` with the host, folder, and any explicitly chosen model and mode — the same call web makes), then the message — with any attachments uploaded into the new chat — goes through the ordinary composer send path, and the screen replaces itself with the new chat's detail. The destination is always that brand-new chat. The row is seeded from the returned id and folder before the message is echoed, so the surface holds the chat and is subscribed to its events on every reconnect (`12-error-and-offline.md` § Replay vs history cursors); the host's spawn confirmation reconciles it in place. Sending with no host or no folder chosen is refused with a message saying which, keeping the text. A create the server refuses is one error toast with its reason, the text and attachments stay for a retry, and any row the refusal already seeded is removed. A spawn the host refuses later arrives as a failed turn in the chat the user is looking at (`12-error-and-offline.md` § Principles).

Backing out leaves no chat behind. The unsent text and attachments stay as the new-chat draft and are there the next time the screen opens (they are cleared by a successful send). Once Send has created the chat the send is under way: the screen replaces itself with the new chat at once, and the first message shows there as pending while its attachments upload; a failed upload stays in that chat as `Not uploaded` with Retry (§ Composer → Attachments).

Folder picker sheet. The same one-control model as web's popover (`14-design-web.md` § New-chat setup row → folder picker), in a bottom sheet rather than an anchored pop-up. A search box at the top is focused on open, reading "Search folders or type a path". Typing filters the recents list below it by name or path. Typing something path-like (`/` or `~`) switches the list to live path completion on the acting host (the chosen host chip, else the screen's current host, else the only host; with several hosts and none chosen it says `Choose which host to browse.` rather than guessing), daemon-backed the same way web's is (`04-chats-and-folders.md` § Browsing): the first row, `Use <typed path>`, chooses the typed path outright, and each suggestion below it — the directory's entries starting with the partial last segment — completes the text to that entry plus a trailing `/` when tapped, so the user can keep drilling. A completion error is shown in place of the suggestions. Otherwise one list: recent folders, most-recently-used first (the host's registered roots follow, never counted as used), each row showing a folder icon, its plain basename, its short (`~`-relative) path beneath, a host tag, and when last used — never grown to disambiguate a shared basename, since the path and host tag already do. Folders only a job spawned a chat in are not offered, and the screen never opens on one. With more than one host registered, `All` and one chip per host sit above the list, narrowing it to that host; path mode and Browse… act on the selected chip. A footer row reads `Browse…`, opening the host directory tree inside the sheet: it opens at the host's browsable roots (`04-chats-and-folders.md` § Browsing), entries drill in on tap, a breadcrumb (name, full path muted beneath) appears once drilled in, Up a level goes to the parent, and `Use this folder` selects it and dismisses the sheet; a back row returns to the folder list. A browse error is shown in place of the list. Tapping the backdrop or the system back gesture dismisses the sheet without changing the choice. The job editor's Folder field (spawn, persistent chat and run-a-command actions) is the same pill and the same sheet: picking a folder there sets the job's host and folder together, and a typed path replaces the former `Custom path…` option.

### Model picker

The model pill reads the model the chat will start on and opens the chosen host's catalogue (`02-daemon.md` § Model catalogue) as a list with a tick on the current one. It preselects that host's last-used model (`04-chats-and-folders.md` § Spawn), and a spawn the user never touched the pill for names no model at all, so the host resolves that itself rather than the phone pinning a model on its behalf.

Wherever the pill sits — the new-chat screen's Model row or the composer — its list opens over the composer at the foot of the screen, where the permission-mode list opens, never under the header where the screen's own ⋯ menu drops. The list is live and never stood in for: it reads `Loading models…` until the catalogue arrives, and a failed load reads the reason in its place. The pill still names the model in force while that is true, so a chat can be started with the catalogue unavailable. Choosing a model closes the list; tapping the backdrop dismisses it and changes nothing.

## Manager incoming-call UX

Mobile equivalent of the desktop overlay, but at the OS level:

- Phone shows the native incoming-call UI via Android `ConnectionService`. Headphones tap or call-screen button accepts.
- Foreground service starts; `AUDIOFOCUS_GAIN` is requested so other media (Spotify, podcasts) duck or pause for the call.
- Accept → opens the Manager chat with the call bar docked (§ Voice states).
- Decline / 30s timeout → falls through to the in-app inbox; phone push suppressed if any surface has a heartbeat in the last 30s (see `09-notifications.md`).

## Push notifications

- Expo's push API (Android only).
- Notification permission is requested up front in the first-launch priming flow (see § First-launch permission priming), not lazily on the first notification. Expo push token registered after the grant; re-registered on app update or token rotation.
- Payload: `{chatId, message, channel, priority, deepLink?, actions?}`.
- Tap notification → deep-link into chat, unless the payload carries a `deepLink` the notification's own text names, in which case the tap opens that URI instead via the OS (`09-notifications.md` § `### push`).
- Notification actions (`09-notifications.md` § Notification actions): Reply, Approve/Deny, a question's options, and `patch_notify`'s quickReplies are Android notification actions — RemoteInput for Reply, plain buttons otherwise. Approve opens the app (so Android requires the device unlocked to complete it); every other action runs without opening the app, including from the lock screen. A reply/action is sent over its own short-lived connection rather than the app's live one, since the action may fire with the app merely backgrounded — the same mechanism the Ready List widget's Approve/Deny already uses (§ Android home-screen widgets). A delivered action updates the notification to "Sent"; a failed one updates it to "Not sent — tap to retry" and keeps the typed text for the retry, which a further tap performs.
  Reply and Approve/Deny use a fixed set of actions, registered once at app start, so they are available even for a notification shown while the app has only just woken to handle it. A question's options and `patch_notify`'s quickReplies carry their own text, which the app registers fresh as each notification carrying them arrives — read by Android when it builds the notification, independent of whether the app is running at that moment, but only once the app has run at least once since that specific notification's text was decided. A notification shown before that has happened falls back to Reply.
- A `deepLink` is only followed when the notification's text names where it goes. The link is reduced to its identifying words — its scheme, its host labels, and the words of its path and query, split on non-letters and on camelCase, keeping words of three letters or more and dropping generic URI furniture such as `https`, `www`, `com` and `index`. The link is followed when at least one of those words appears, case-insensitively, in the notification's title or body. A link with no identifying words, or with none the text mentions, is refused: the tap opens the source chat instead and the refusal is logged with the link, the reason and the words looked for. It is never followed silently and never dropped silently.
- A tap that arrives before the app can navigate, which is the normal case when the app was killed, is held and opened as soon as it can be, never dropped in favour of the default screen. A `patch://` link that launches the app is held the same way. A destination that still cannot be opened is reported as an error naming it.
- Opening a chat that is already on screen lands on that chat rather than stacking a second copy of it.
- Presence rule: phone push suppressed if any surface has a heartbeat in the last 30s, unless `priority: 'silent'` or a call ring (`09-notifications.md` § push). `urgent` is suppressed like `normal`; it differs only in its sound, played by the `patch_urgent_alert` channel.
- A batch check-in notification (§ Batch view, `09-notifications.md` § Batch check-in) carries `kind: 'batch'` instead of a `chatId`, and a tap lands on the `Batch` tab rather than a chat — held the same way a killed-app tap is if the navigator isn't up yet.

## First-launch permission priming

On first launch (after pairing) the app requests all the OS permissions it will need up front, so no feature ever hits a cold permission prompt mid-use:

- A brief priming screen explains why each permission is needed, then the app requests them together: microphone (voice notes + calls), notifications (Manager calls, chat activity), camera (taking a photo to attach to a message; scanning device-pairing QR codes), and the phone-call permission needed for Manager incoming calls. Each request states its purpose before the OS dialog appears.
- Requesting up front is correct — the mechanism must be the right one. Each permission is requested through its standard runtime permission dialog (the Allow/Deny prompt). The priming flow keeps the user out of unrelated system settings pages — in particular the Android "Calling accounts" / phone-account screen (the SIM/calling-account configuration UI) is not a permission prompt and must not be opened as part of priming. Registering a Telecom phone account (via `ConnectionService`/CallKeep) is a separate, lazy step tied to actually placing/receiving a call; if a self-managed connection is used it does not require sending the user to that settings screen at all. Priming asks for the runtime grant only.
- Priming is the default path; the older in-context requests remain only as a fallback for a user who declined at priming (the feature explains it needs the permission and links to system settings). A declined permission reports why the feature is unavailable.
- The flow runs once — gated on a "primed" flag in local storage — and does not re-nag on subsequent launches.

## Mobile equivalent of the menu bar

Desktop has a menu-bar dropdown for at-a-glance status without opening the app. Mobile has two equivalents, both tucked into the OS:

- Persistent foreground notification (when voice or any chat is `running`) — shows in the system shade with one-line live status ("3 chats running, 1 needs you") and a Manager quick action that opens the voice-note overlay.
- Long-press the launcher icon (Android shortcut menu) for `Manager voice note`, `New chat`, `Open Speakers`.

Neither is rich enough to replace the full app — they're for the moments when you don't want to open the app at all.

## Share into Patch

Patch is on the Android share sheet for text, links, images and any other file, one or several at a time. Sharing opens a destination picker: what is being shared (the text, and a chip per file with a thumbnail for images), Start a new chat, then the user's chats (archived and deleted ones excluded), most recent first, with a search field filtering them locally by the same rule as the Chats tab's one-character filter (§ Chats tab → Search). Cancel discards the share.

Nothing is sent. The share lands in the chosen destination's composer — an existing chat's, or the new-chat screen's (§ New chat flow) — and the app opens there: shared text is added to whatever is already typed in that composer, and each file becomes an ordinary attachment chip that uploads through the composer's own path on Send (§ Composer → Attachments). A shared file is copied into the app's own storage the moment it arrives, so it is still readable when the user presses Send; a file that cannot be read is reported by name, and the rest of the share still goes through. A share that arrives while Patch is already running is delivered the same way as one that launches it.

## Native specifics (Android)

- Foreground service while voice is active (OS requires it). Active media-style notification in the system shade with end-call action; user can dismiss/end the session from the notification.
- Audio focus management: voice agent requests `AUDIOFOCUS_GAIN_TRANSIENT_MAY_DUCK` (or full `_GAIN` for incoming Manager calls) before speaking. Media apps (Spotify, podcasts) duck/pause for the duration; resume when voice releases focus. Standard Android VoIP pattern.
- Bluetooth headphone routing: follow OS default; route audio to the active output device.
- ConnectionService integration for Manager-initiated incoming calls.
- Expo's push API for push. High-priority data messages for Manager-call wake-ups; normal-priority for routine notifications.

### App icon (adaptive launcher icon)

The launcher icon is a proper Android adaptive icon so the OS masks it to
the device's icon shape (circle / squircle / rounded square) instead of showing
a bare square.

- Layers. Background = solid tile green `#3A5E2C` (`@color/iconBackground`);
  foreground = the Patch "p" glyph, RE-CENTRED into the adaptive safe zone. The
  source art (`assets/icon.png`) places the glyph low and left of centre, so
  using it raw would clip the descender under a circular mask — the foreground
  asset (`assets/adaptive-icon.png`) fixes the glyph at ~50% height, centred. A
  `monochrome` layer (`assets/adaptive-icon-monochrome.png`) backs Android 13
  themed icons.
- Generated resources (committed under `android/app/src/main/res`):
  `mipmap-anydpi-v26/ic_launcher.xml` + `ic_launcher_round.xml` (the
  `<adaptive-icon>` definitions), `mipmap-<density>/ic_launcher_foreground.png`
  and `ic_launcher_monochrome.png` at all five densities (mdpi→xxxhdpi), and the
  regenerated legacy raster `ic_launcher.png` / `ic_launcher_round.png` for
  API < 26. The manifest sets both `android:icon` and `android:roundIcon`.
- Source of truth. `app.config.ts` declares `android.adaptiveIcon`
  (foreground + monochrome + `backgroundColor`) so a future `expo prebuild`
  regenerates the same set; the committed native resources are kept in sync with
  it.
- Cold-start splash. The splash shows the same square logo on the paper
  background, whole. Android masks the splash icon to a circle 192dp across in
  a 288dp canvas, so the square is sized to fit inside that circle, corners
  included (no more than 192/√2 ≈ 136dp wide).

## Native feel & launch performance

Patch is a fully native Android app (bare-workflow Expo / React Native).

### Instant open (read cache)

- A small on-device cache (MMKV) mirrors the chat list rows — the roster
  metadata the Chats tab renders. On launch the UI paints from this cache
  synchronously, before any network call, so the chat list appears immediately,
  exactly as it was last seen. Message timelines are not cached; a chat's
  transcript is always loaded live.
- The cache is a convenience read-mirror of server state. The roster fetch and
  the live WebSocket stream are authoritative and replace it wholesale, so a
  chat deleted or renamed elsewhere cannot survive from cache, and the cache
  needs no offline-edit or sync-conflict semantics. Un-acked user input is not
  cache state: it lives in the surface's own pending/queued input tracking
  (`12-error-and-offline.md` § Guaranteed input delivery), which mobile
  implements like every other surface.
- After first paint, `bootstrap()` opens the WS and reconnect-replays
  (`chat.replay {fromSeq}`, per `12-error-and-offline.md`) — only for the chats
  whose transcript this surface already holds (the open chat and any with a
  rendered timeline), rather than the whole roster; the live stream supersedes the
  cache. The HTTP `GET /api/chats` fetch runs as a background catch-up and is
  the only roster load on a cold start.

### Snappy interaction

- Lists render at 60fps; chat rows and timelines read from in-memory state.
- Sending a message echoes optimistically: the store appends a local user row
  with a negative `seq`, and the real event reconciles when it lands.
- Navigation, tab switches, the voice-note overlay and the call bar appear
  without a network round-trip.

## Offline / error states

Connection has four states — `connecting` · `connected` · `reconnecting` · `offline` — and the WS-to-server link and the host presence are tracked separately (the server can be reachable while the host is down; the two stay separate indicators).

- No offline flash on load. On first launch the app is `connecting` and shows nothing — no connection dot in the Chats header, no banner. The "offline"/"reconnecting" treatment starts once a connection has been established and lost. The amber banner is for `reconnecting` (was connected, dropped) and `offline` (a connect attempt has failed) only.
- WS reconnecting — amber banner at the top of the chat list ("Reconnecting…"); composer disabled; inbound shows queued status. The banner follows the disconnect grace (`12-error-and-offline.md` § Surface connection state model): it shows only after the link has been down for 3s with the app in the foreground, so opening the app after Android dropped its socket in the background does not flash it. Diagnostics still report the true state immediately.
- Diagnose is always one tap away. Both the WS banner and the host-offline banner carry a Diagnose action opening the connection diagnostics screen (`12-error-and-offline.md` § Connection diagnostics screen): credential / server / agent-link / WebSocket checks with their real detail text, Retry now, and Copy report (which also states the route — the server's host, or the relay it goes through — since a phone aimed at the wrong server looks exactly like a dead one). The screen takes over the window only when this phone has yet to connect and two attempts have failed; it is dismissible either way, and outside the takeover the app behind it stays navigable.
- A host being offline is a first-class, explained state, not silent degradation (see `12-error-and-offline.md` § Host-offline UX). When the app knows a host is offline:
  - A persistent banner names the host, states that it is unreachable and that messages will be queued and sent when it reconnects, with a tap-through to Settings → Hosts. It is scoped to that host's chats, and goes app-level when every host is offline.
  - Navigation stays fully available — the user can read history and browse chats/settings everywhere.
  - The composer stays usable and queues: a message into an existing chat, or an editor save, is accepted, shown in the queued style, and delivered on reconnect (`12-error-and-offline.md` § Host-offline UX). Spawning a new chat on an offline host is refused up front, matching the folder picker (§ Folder picker sheet). Only voice note and voice call, which carry ephemeral audio, render visibly disabled with a reason naming the host.

## Find in chat
