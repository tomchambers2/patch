# Server

One Node/Fastify process. Deployed on a box with a public address and HTTPS, it is the only component that needs to be internet-reachable. A server without such an address (one a desktop app runs for itself) is reached through a relay instead (`10-auth.md` § Relay).

## Responsibilities

- Account + host registry. User has one account (Ed25519 `publicKey`). Each host machine's host registers separately (`daemonKey`) via QR-code linking, and the registry holds a record per host: `daemonId`, host name, platform, version, and last-seen state. Hosts are peers, and any number of them may be registered.
- WebSocket hub. Persistent connections from surfaces and every host; server routes events by `(account, chat)`, and a chat's `daemonId` selects the host a surface event is delivered to. Hosts dial out to the server and hold the connection.
- Chat state. The server owns what it last knew about every chat, not only its transcript: the mirror of each chat's activity, status, host, job, folder, last-updated time and the rest of what `chat.state` carries is saved to `/data/chat-registry.json` as it changes (a second after the last change, and on shutdown) and read back at startup, together with the set of chats it has seen announced. A restart therefore begins from what the server knew, and a `chat.state` for a restored chat is accepted without the chat being announced again. A restored chat is unconfirmed until its host reports it; when a host closes its re-announcement with `folders.list`, any restored chat of that host it did not report is dropped, so a chat removed while the server was down does not linger. The mirror also keeps when each chat was last seen working, so a restored idle chat can be told from one that has not started. A host's report always wins over what was restored. Anything that reads a chat's activity — the job concurrency gate (`08-triggers-and-jobs.md` § Concurrency), the sweep, the completion push — sees the restored state from the first moment.
- Chat→host binding. The server records which host each chat belongs to and routes that chat's events to it alone (`04-chats-and-folders.md`).
- Cross-host relay. A cross-chat tool call naming a chat on another host arrives from one host and is delivered to that chat's host, with the response relayed back to the caller (`03-wire-protocol.md` § Cross-chat tools). A call for an offline host is answered with an error naming it rather than buffered, since the caller is waiting inside a turn.
- Relay presence. With `PATCH_RELAY_URL` set it holds its relay channel and ends devices' encrypted sessions on its own loopback address (`10-auth.md` § Relay); `GET /api/relay` reports whether it is reachable that way.
- Message log. The server is the log of record for every chat's transcript. A finished event a host sends (a message, a tool call or result, an error) is written to the chat's append-only file (`/data/chat-logs/<chatId>.jsonl`) before it is broadcast to any surface, so what a surface has seen live is already on the server's disk; a person's own message is fsynced at once, the rest reach disk as the operating system flushes them. A resend of an event the server holds (a host replaying after a dropped link) is kept as it is and not broadcast again; the same event with a changed payload replaces the held one and is broadcast; a different event at a seq already held is refused and logged, never broadcast. Live streaming (text deltas, tool progress, state) is not part of the log and never waits on a write. A moment after commits the server tells the chat's host how far its log reaches (`chat.committed`, one frame per chat for a burst), and the host's numbering never falls at or below it. While a chat's host is online the host's own log answers replays; while it is offline the server answers replays and history reads from its log (`chat.replay`, `GET /api/chats/:id/history`, marked `fromServerCopy`), so the chat stays readable. The server and a host keep their logs of a chat in step: every `chat.state` carries `lastSeq`, how far the host's own log reaches, and when the two differ for longer than a couple of seconds the server acts. A host ahead is asked (`patch.log_sync.request`) for what follows the server's high-water mark and answers from its own log in batches (`patch.log_sync.batch`), which the server takes as live events, so what a dropped link or a full resend buffer lost is recovered. A host behind, because its log was lost or another host ran the chat past it, is sent what it lacks (`patch.log_restore`), so a host's local log is a cache the server can rebuild. A chat the server holds none of is not copied from the host on first sight. A tool result over 4 KB is kept in the log as a reference to a body stored once under `/data/chat-logs/blobs` (the shape a host's own log uses), so a replay is small and `GET /api/chats/:chatId/blob/:sha` serves the body from the server, with no host online, before asking a host.
- Server-run queue and Manager failover. The server holds the messages behind a running turn for a host that can take them and decides when each goes in (`04-chats-and-folders.md` § Message queueing). It asks another host to run the Manager while the home host is offline (`06-threads-manager-speakers.md` § Manager failover).
- Held messages. A person's message to a chat on an offline host is held by the server in `/data/held-input.json` and sent when that host attaches. A host removed from the account loses what was held for it, and a message older than seven days is not sent.
- Waiting messages. The server keeps each chat's queue from `chat.queued` and `chat.dequeued` and re-sends the waiting messages to a surface that asks for the chat's replay (`04-chats-and-folders.md` § Message queueing).
- Push fanout. Expo's push API for Android push. Push tokens registered per surface. Android only.
- Webhook ingress. `POST /api/webhooks/:jobId`. Payload matched against the job's JSONata filter; action dispatched to the host the action names. Todoist instead uses one shared `POST /api/webhooks/todoist` that fans an event out to every todoist-trigger job whose filter passes, since a Todoist app has a single callback URL (`08-triggers-and-jobs.md` § Todoist).
- Cron scheduler. Server runs an in-process scheduler that fires `cron`-trigger jobs at their next match, evaluating each expression in the trigger's own timezone. Each tick produces a payload (`{ firedAt }`) and dispatches the job's action to the host that action names, same as a webhook trigger. See `08-triggers-and-jobs.md`.
- Broadcast log. Every notify passes through the server, so it is the server that records one against the mediating thread when the channel is `speakers`, and serves those records to the home host when the user replies on that channel (`09-notifications.md` § Broadcast context).
- Presence tracker. Every connected surface heartbeats (`ping` every 10s, timeout at 30s). Drives notification routing (see `09-notifications.md`). Host presence is tracked per host.
- Host build distribution. Serves the current host artifact per OS/arch and its version manifest, which back host self-update and the install command a surface offers for a new host (`02-daemon.md` § Runtime and installation).
- Job definitions. Stores job JSON files (`/data/jobs/*.json`), watches for changes, notifies the host.
- Manager sweep gate. Watches every chat on every host for the conditions that make a sweep due (`06-threads-manager-speakers.md` § The sweep), and asks the home host to run one when they are. It belongs here because it is the only component with the cross-host view; it decides nothing beyond when a sweep is due and which chats are candidates — the decision and the actions are the home host's.
- Thread rotator. Checks, on a steady tick, whether it's a special thread's scheduled rotation time (`06-threads-manager-speakers.md` § Session rotation); when it is, asks its host to rotate it (`chat.rotate_request`). The host owns the actual session swap and digest; the server owns only the clock, same split as the sweep gate.
- Settings. The source of truth for every setting that is not tied to one machine, including backend accounts and provider keys (§ Settings).
- Composer drafts. One unsent-composer-text entry per existing chat, owned by the server rather than the host so it is available even while a chat's host is asleep (`14-design-web.md` § Composer, `03-wire-protocol.md` § Composer drafts) — stored in `/data/composer-drafts.json`.

agent sessions, chat-history storage, LLM calls, and voice processing (Whisper + Kokoro for phone, web, and standalone-device surfaces) all belong to the host (see `02-daemon.md`, `04-chats-and-folders.md`). Surfaces fetch chat history on attach.

## Settings

The server holds the account's settings and every host runs from the copy the server last sent it. A host never changes a shared setting itself. The same holds with one machine or many: a single-machine install runs the server and its host side by side.

Shared by every host, stored on the server:

- Backend accounts: the Claude and Codex credentials, their order and each backend's account strategy (`10-auth.md` § Backend credentials).
- Provider keys (`02-daemon.md` § Provider keys).
- Agent behaviour: default model, default permission mode, auto-resume after a limit, question expiry, chat-name interval, and the layers in `14-design-web.md` § Agent behavior.
- Voice: the Kokoro voice and the voice config matrix (`07-voice-app.md`).
- Claude Code `settings.json` (`02-daemon.md` § Claude Code settings).
- Manager sweep and quiet hours, the voice address word, and the special threads' model and rotation schedule.

Held by each host, because they describe that machine: its name and home-host flag, its project folders, its installed components and self-update, Claude Code memory (stored under that machine's project paths), and what it has learnt at runtime about which accounts are out of credit.

Settings are stored in `/data/settings.json`. Credentials and provider keys are stored in `/data/secrets.json`, encrypted at rest with `/data/secrets.key`, which the server makes (0600) the first time it starts with no secrets file; there is nothing to configure. The key keeps the secrets out of anything that copies `secrets.json` on its own; it is no protection against someone who can read all of `/data`. If the secrets cannot be read — the key is missing, is not a key, or does not decrypt the file — the server still starts: it sends hosts no settings (a snapshot without the accounts would sign them out), refuses every change to an account or key with 503 `secrets_unreadable`, and puts the reason and the fix on `settings.changed.problem`, which Settings shows at the top of every page. A secret goes out only to hosts, over their host link. A surface only ever sees where a secret came from and its last four characters, and nothing logs a value.

Every change goes through the server: a surface over REST, the CLI through the server, an agent through the `patch` tools. The server validates it, commits it, and sends every connected host a `settings.snapshot` carrying a version. A host also receives the snapshot whenever it connects, so a host that was offline is current as soon as it is back. The host writes the snapshot to `~/.patch/settings.json` (mode 0600, atomic), applies it, and answers `settings.applied` with the version, or with the reason it could not apply it. Settings shows any host that is behind or refused, by name. While the server is unreachable a host keeps running on its last snapshot, and a settings change made on that machine is refused, naming the server, rather than applied locally.

A host that connects for the first time since settings were shared is asked, once, for everything it held on its own — its accounts, its provider keys and, for the first host only, its settings — before it is sent a snapshot. Accounts already held are not added twice: a second copy of the same Claude organisation or the same OpenAI login is dropped, and a label that would read twice gains the host's name. A host whose import fails keeps running on what it held and is asked again when it next connects.

Some values start on a host and still end on the server. Provider refresh tokens stay on the server, which renews them serially and sends only access credentials to hosts (`10-auth.md` § Backend credentials). A successful sign-in on one host replaces the shared login for that credit source. A value found on the machine — the backend's own login, a provider key in the host's environment, or a Claude Code `settings.json` changed there (`02-daemon.md` § Claude Code settings) — can be adopted from Settings, which asks that host to send it to the server as the shared value.

## Starting with no settings

A server starts with nothing configured. It listens on port 3000 and keeps its state in `~/.patch-server/data` (`$PATCH_SERVER_HOME/data` when that is set), made on the spot. The first time it starts it makes what it needs in that directory, 0600: `secrets.key` (§ Settings) and `internal.token`, the voice-session secret each host is handed when it is registered (`10-auth.md` § Host registration). `PATCH_DATA_DIR` and `PATCH_INTERNAL_TOKEN` override them. A value that is set and unusable (a data directory that does not exist, a token under 16 characters) stops the server rather than being quietly replaced, and so does a token file that holds no token.

## Stack

- Node 20+, TypeScript.
- Fastify for HTTP + WebSocket.
- Flat files for persistence initially (`/data/jobs/*.json`, `/data/registry.json`). Migrate to SQLite only if presence/replay complexity demands it (see `12-error-and-offline.md`).
- Commit before broadcast. Server only emits over WebSocket after the underlying flat-file write is fsync'd (or, when SQLite is used, after the transaction commits). Otherwise a crash mid-write leaves clients seeing state that was never persisted.
- `ws` for WebSocket; protocol defined in `03-wire-protocol.md`.
- No E2E encryption to server (we own it and the host). TLS termination only.
